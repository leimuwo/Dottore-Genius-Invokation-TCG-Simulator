## 1. 决策

| 项 | 决定 |
|---|---|
| 逐决策观测 | **实体对齐词元**：每个活着的实体 1 个词元 + 少量动态标量 |
| 静态内容（牌表 `initial_deck`、角色定义、max_hp/element/weapon/id） | 挪到**每局一次**的上下文向量（**只对自己**：对方牌表被 `hide_secrets` 换成 `OmniCard×30`，见 §5.5） |
| 填充位 | 直接丢弃（实测 1 271 维） |
| 词元预算 | 实测 p50=41 / p90=47 / **p99=50** / max=56；上限 256，余量 ≥5× |
| v1 的「每段 1 个词元 = 26 词元」 | **否决** |

实体→词元映射：手牌每张 1；角色每只 1（138 维字段过小 MLP）；状态/summon/support 每个 1；
骰子 1（8 种元素计数向量）；deck/used/gained 各 1（集合池化）；效果栈每层 1；`game_basics` 1。

观测按席位取（`perspective_view(seat)`），与 D-A 的 `obs(seat)` 对齐。

## 2. 为什么 v1 的两条结论被撤

### 2.1 「常量维 2538、可裁到 247」是采样假象

v1 每局只取**前 4 个决策态**（共 480 个样本），那时手牌少、效果栈空。
打满整局（17 998 个决策态）后：常量维是 **2 219**，而且不是一个数而是一个结构：

| 类别 | 维数 | 含义 |
|---|---|---|
| **P 填充位** | 1 271 | 容量 − 占用；永远为 0 |
| **S 静态位** | 1 044 | 局内从不变化，跨局才变（卡牌定义/牌表内容） |
| **D 动态位** | 463 | 局内变过 → 必须逐决策观测 |

同一脚本对「前 4 态」口径给 2 569、对全量给 2 219，**差 350 维**——这就是假象的量级（判据 C5）。
所以"裁到 247"不成立：该问的是"这 2 219 维各是什么"，不是"能删多少"。

### 2.2 「26 个词元」粒度不够

把 1000 维效果栈段、414 维角色段各压成 1 个词元，模型分不清"哪个角色被打残"。
换成实体对齐后 p99=50：量级翻倍，但仍远低于 256。

## 4. 三个实现坑

1. **尾部填充是当前实现的巧合**：卡牌 code 先升序、再追加 0；骰子/状态/效果栈同理。
   按位置切"尾部 0"能work，但不是契约 —— 所以策略层用实体对齐 + 容量校验，不硬编码下标。
2. **`num_cards()` 会说谎**：`Cards` 允许**负计数**（实测 `ChangingShifts: -1`），
   `num_cards()=sum(values)` 比真实张数少，而 `encoding` 按 `Counter.elements()` 给真实张数。
   实测 **57/17 998** 决策态触发（0.32%）。本脚本改为**从编码本身数占用**，
   负计数作为独立引擎问题（E5）登记，不在本决策里修。
3. **效果栈在决策态几乎总是空的**：p50=0、p99=5、max=10；但**解析过程中**最大深度到 **20**
   （测试套件实测）。所以"10 个词元"是决策态上限，不要为它做很重的编码器。

| 判据 | 结果 |
|---|---|
| C1 分段覆盖 0..2777 各一次 | PASS |
| C2 每段 容量 × 字段宽 == 段长 | PASS |

| C4' 容量公式给出的填充位 100% 落在"局内恒定"里 | PASS |
| C5 前 4 态口径 − 全量口径 ≥ 100 维 | PASS（350） |
| C6 词元 p99 ≤ 256 且 max ≤ 320 | PASS（50 / 56） |

## 5.5 T1 交叉确认（D-C × `CardEnv` 协议）

T1 的验收原话是「同 seed 两进程 obs 逐位相同」，而 D-C 的数字是在**同一进程内**测的，
所以补 `analysis/probe_obs_vs_t1.py`（子进程跑同一段采样，结果走文件回传）。

| 判据 | 结果 | 含义 |
|---|---|---|
| X1a 初始决策态 obs 跨进程逐位相同 | **PASS**（修 E6 后） | 修前 FAIL：aura 段迭代 `frozenset` |
| X1b 前 30 个决策态跨进程逐位相同 | **FAIL** | 首个分歧 seed=0 idx=4，差的是**骰子段**（8..15） |
| X2 视角视图词元 p99 ≤ 256 | PASS（p99=48, max=51） | 与全量口径几乎一致，结论不受 `perspective_view` 影响 |
| X3 观测泄漏 | PASS（0/20 改变；正对照 20/20） | 换掉对方手牌身份（张数不变）后 obs 不变 |
| X4 静态牌表按席位 | PASS（20/20） | 自己牌表可见；对方被换成 `OmniCard×30`，对真牌表不变 |

三条结论：

1. **E6（已修）**：`ElementalAura.encoding()` 迭代的是 `frozenset`，枚举成员 hash 依赖进程内
   `id` → 同一状态两进程 obs 不同。改成声明顺序 `AURA_ELEMENTS_ORDERED` 后 X1a 转绿。
   这个缺陷**在同进程内测不出来**，只有跨进程比对能逼出来。
2. **E7（未修，卡住 T1）**：轨迹本身跨进程不一致。`dice.py:642`
   `random.choice(tuple(ActualDice._LEGAL_ELEMS - excepted_elems))` 从 `set` 抽样，
   骰子元素顺序逐进程变化 → idx=4 处两个进程拿到不同的 8 颗骰子。同类站点还有
   `card.py:2489/2676/3497`、`support.py:219`。**在 E7 修完之前，T1 的验收条款无法成立。**
3. **静态上下文是单边的**：`hide_secrets()` 把对方牌表换成 `OmniCard×30`，所以
   "牌表进每局一次的上下文向量"只对**自己**成立；对方只能进一个常量（B3 的既有决策）。
   §1 表格里那一格据此修正。

> X1b 不改表示结论（X2/X3/X4 都绿），但"数字可复现"降级为**单进程内**；T7 的固定套件 + CRN 也卡在 E7。

## 6. 已知失真

1. **跨进程漂移**：同一脚本跑三遍，P/S/D = 1 288/1 025/466、1 292/1 012/474、1 271/1 044/463
   （原因 = E7）。结论只用**量级与结构**（P≈1.3e3、S≈1.0e3、D≈0.47e3），不做精确复现断言。
2. **占用分布来自随机策略**：`RandomAgent` 的手牌/状态占用偏低（例如 supports 打到 4 个满）。
   换成会打的策略后占用会上升 → p99 词元数（50）是**下界**，M1 需重测一次，但仍远低于 256。
