# 生成式软件工程 · 重要思想总结

> 基于 jyy（蒋炎岩）《生成式软件工程》8 讲讲义整理。
> 面向读者：AI 方向研究生，目标是**用 AI 做好开发与项目管理**。
> 写法：每一单元给出「核心一句话」→「重要观点」→「立刻能用的做法」。

---

## 全课主线（先看这一页）

这门课反复在讲同一件事：**软件工程 = 补上 Intent → Specification → Implementation 之间的 gap。**

- **AI 把 implementation 变便宜了**，于是杠杆从"会写代码"转移到了**需求（intent→spec）与架构（spec→impl）**。
- 但模型有三个稳定缺陷，所有方法都是为了对冲它们：
  1. **急着完成**（强化学习奖励"做完"，所以它会立刻上手、往"最快的脏路"上走）；
  2. **是 prompt 的舔狗**（过度遵循你的话，包括你写错的、模糊的话）；
  3. **不会主动补全你没说出口的约束**（你脑子里的 CSGO 和它生成的 CSGO 不是一个东西）。
- 因此全课的方法论可以浓缩成三句：
  - **把任务变成可验证的**（Verifier 是第一原则）；
  - **每一步都检查**（开发者不可信 → CI/门禁）；
  - **设计一片会生长的解空间**，而不是选定一个解。

**一句话自检**（第 1 讲提的那个问题）：导师问"我为什么要招你，而不是买一个 200 美元的 Claude Max 订阅？"
课上给的参考答案是：**我能找到值得解决的问题，用证据让坏方向及时停下，并对长期结果负责。** 这句话贯穿全课。

# 第一单元 · 欢迎来到未来：AI 时代为什么要学软件工程

**核心一句话：古法编程已死，软件工程未死——你的想象力限制了你的 Agent 的上限。**

### 重要观点

1. **计算机史的一条主线：把昂贵的能力变成日用品。** Altair 8800 → 互联网 → 移动互联网 → ChatGPT。每一次都是"原本只有精英能用的能力，变成所有人的日用品"。所以"AI 替代了我学的知识"本身就是这个规律的又一次发生，不是意外。

2. **两种焦虑，本质是同一个。** ①AI 替我上完大学我什么都没学到；②我认真学了四年却发现 AI 都会。共同点是：**你训练的能力和模型训练的能力重合了**（都是"5 分钟做出一道题"），而模型数据和反馈信号更多，所以它做得更好。

3. **三个空间与两个 gap（全课最核心的图）。**
   ```
   Intention（你脑子里想的）
       ↓  gap ①：翻译 / 澄清
   Specification（功能、架构、接口、约束）
       ↓  gap ②：实现 / 验证
   Implementation（代码与部署）
   ```
   软件工程失败的定义在大模型时代**没有变**：要么做出来的不是你要的（gap ①），要么实现不满足规格（gap ②）。而且**越上游的 gap 杠杆越大**——上游微微变一点，下游产生巨大变化。

4. **模型是在"猜"。** 后训练让它形成了"疯狂立即上手、尽快完成任务"的倾向。它能越来越快地做简单任务，但这和人解决问题的方式不一样——人会在动手前设计一个中间层，模型的第一反应是"做题家"。

5. **人月神话在 AI 时代的翻版。** 一个已经开始失败的项目，加人不会救活它；同样，**AI 已经开始产生 slop 的时候，你投入更多 token 也只会让它更失败**——它会不断在失败的东西上再浮一点，直到你付不起 token 为止。（对照：教务系统每年加功能。）

6. **学习路径的倒转。** 过去是 bottom-up（先学 C → 再学软件工程）；AI 时代可以 product-first：**先从产品经理做起**，因为你后期所有事都是 vibe code，你不去控制质量，也不需要理解它。

7. **三个"最能放大个人能力"的用法**（课上的实证案例）：
   - **读书/读论文**：假设已知的都是已知的，把论文里真正新的、最少的东西剥离出来；
   - **看视频/长内容**：图文时间轴 + 只保留对你不 trivial 的部分；
   - **把日常事务流程化**：邮件、发票、待办、打印 → 沉淀成 skill，形成**个人知识飞轮**。

8. **CS 从业者的独特价值：知道边界在哪里。** 普通人也能提需求，但他不知道"怎么把需求编译成 agent 能做的任务"。课上那个统分流水线的例子最典型：头顶摄像头 + 本地离线 OCR（27B 模型）+ **语音播报人工核对** + **脚本算总分（大模型不做加法）**。每一步都是"知道边界"才能设计出来的。

### 立刻能用的做法

- 从今天开始：**先把东西搞出来，再回头复盘理解**（比从零逐点学快得多，但要警惕"理解和好理解的差距"）。
- 建立你自己的信息处理系统：RSS/arXiv/HN/公众号 → skill 流水线 → 有用的知识；然后**定期问 AI："我这一天干的这些事，还有没有提升空间？"**
- 有一个可交付的"简历项"：不是论文列表，而是**能点开的链接 + 你能讲清楚设计中的了不起之处**。

# 第二单元 · 软件工程的来龙去脉：gap、瀑布模型与 UML 的野心

**核心一句话：软件工程的历史就是一部"试图补上 gap"的历史，而那些失败的方法论，其 first principle 今天仍然有效。**

### 重要观点

1. **软件不软，需求出自人脑。** 与桥梁/炼钢相比：
   - 传统工程的需求来自物理世界（只能适应、不能改造），约束出厂就定；
   - 软件的需求是"拍脑袋想出来的"，高度定制化，连接物理、社会和人的偏好。
   - 所以**连制定 intent 的人自己都没想好各种 corner case**（先修课是硬限制还是软限制？谁能 override？）。

2. **软件危机的三个同步失控**：进度无法预测、成本超支、延期交付。

3. **Dijkstra 的 goto 之害，真正的意思不是 goto。** Linux 内核里满是 goto（`goto release` 统一释放资源）。他讨论的是：**希望你写出人能读、能维护的代码**。"程序员水平随 goto 密度上升而下降"是一句暴论，但背后的诉求是 maintenance。

4. **The Humble Programmer 与 nicely factored solutions。** 为什么会有软件危机？因为机器越强，承担的 intent 越多，不确定性越多，实现越复杂。解法是**良好的分解**（nicely factored solutions）——这也是"架构"的雏形。

5. **Hamilton 与防御性编程的起点：The never going to happen can happen。**
   她假设软件在任何时候、甚至违反假设的情况下依然要能工作。**这就是软件工程的起点。**
   对照：你刷 OJ 时有一个隐藏假设——"题目是对的、题目是可做的"。你应该假设的是**开放世界**：题目可能是错的、条件随时会变、题目可能会变成另一个题目。

6. **IEEE 的定义：把个人英雄主义变成 checklist。**
   关键词：**有纪律的（disciplined）、可量化的（quantifiable）、覆盖全生命周期（development / operation / maintenance）**。
   变化在于：以前需要一个天才 leader；现在只要 checklist 1..10 都打勾，失败概率就小很多。

7. **Royce 1970 的瀑布模型是在批判瀑布模型**（开山之作被误读最严重）。
   它的 first principle 极其漂亮：
   > **测试是整个链条上第一个"物理事件"。**
   在程序真正跑起来之前，文档、设计都"随便做做"，没有保证。漂移只有在测试时才爆炸，于是成本被放大。

8. **Doing it twice / preliminary pilot program = 1970 年版的 MVP。** 设计先行，先做一个不完备但能体现功能的试验系统，**因为它的迭代成本低**。

9. **用今天的实践回读经典（三种读法都成立）**：
   - **TDD**：缺陷发现得越晚，返工代价越大；
   - **敏捷**：不是 doing it twice，而是 doing it **infinite many times**——让关键假设尽早遇到证据；
   - **Data dependency graph**：把每个阶段当成 program，artifact 之间是 DAG。测试失败要向上追溯，**依赖 D1 的全部作废**，cost 随发现时间指数上升。
   - 结论：瀑布 = BFS 一次性铺开所有层、最后才测试；**敏捷 = DFS + MVP**，走通优先级最高的一条依赖，再向右扩展一层。

10. **语言的阶梯：formal 程度越高，gap 越小。**
    ```
    自然语言（需求文档）→ checklist/决策表（半形式）
    → 设计语言/DSL/UML（类图、时序图）→ 编程语言 + 契约（require/ensure）
    → 形式化证明（编译即证明）
    ```
    文档的最大缺点：**写文档的是人，人会产生幻觉；人和人对不齐**（你甚至和下一时刻的你对不齐）。

11. **质量方法的谱系（都值得学）**：
    - **checklist / 决策表**：给 nonsense 赋予语义，避免遗漏和矛盾；
    - **QuickCheck**：让人描述 property，由工具生成输入寻找反例——因为你做任何事都会错，包括那些隐含的 specification（不 crash、无空指针、资源不泄漏）；
    - **traceability / 需求追踪矩阵**：把 data dependency graph **显式地建出来**；
    - **Design by contract**：Eiffel 把 Hoare 三元组写进代码（`require` / `do` / `ensure`），鼓励**先写契约再写实现**。

12. **UML 死了，但它的 first principle 一直指导我们。**
    UML 的假设是"自然语言和形式语言不能对齐"，所以需要一层层中间语言。**今天这个假设被推翻了**——自然语言可以和任何东西对齐。但它回答了那个根本问题：**哪些 intention 必须定死，哪些留白。**

13. **教科书是有损压缩，现在不再必要。** 一手资料永远更好：读 Royce 原文马上看懂，读经过三四手消化的教材反而看不懂。（课上现场让 AI 解释"瀑布模型是怎么被误读的"，一路追溯到灌水教材。）

### 立刻能用的做法

- **每接到一个任务，先画出 data dependency graph**，而不是立刻写代码。它直接告诉你：哪里是高风险区、改动会波及多少东西。
- 遇到"经典方法论"，**去读一手原文**（让 AI 帮你把原文入库、提取图片、对照阅读），再自己判断它被误读成了什么。
- 写代码时加 contract（`require` / `ensure` / assert）；先定测试用例再写实现，哪怕只是 prompt 里让 AI 先写测试。
- 记住 Royce 给你的那把尺子：**一切补救的本质，都是把发现问题的时间点提前。**

# 第三单元 · 软件仓库管理（上）：从"作业 V1、V2"到 Git 的第一性原理

**核心一句话：Git 是用 Atomic Change 推进的快照；而真正难的部分不在命令，在于"惊人的注意力"。**

### 重要观点

1. **从需求推导出工具。** 需求：万一改错了，我想回到上一个版本 → 土办法：作业 V1/V2/最终版（每次复制目录）→ 抽象：项目 = 一个目录 → 命令行工具：list 版本 / 切回版本 → **简化版 Git 诞生**。再加一个需求：和室友同步、两人改同一个文件 → **分支 / 合并 / 冲突**被发明出来。
   **结论：你完全可以从 first principle 自己发明 Git，这个过程本身就是最好的学习方式。**

2. **SVN 走错的路：存 delta。** 它高效，但项目一大，回到过去某个版本就得一个个往回退。Git 的模型干净得多：**存快照（snapshot）**。

3. **Git 的底层就是持久化数据结构**：只复制到根的路径，其余用指针（copy-on-write）。三类对象：
   | 对象 | 存什么 |
   |---|---|
   | blob | 一个文件的内容（字节序列） |
   | tree | 一个目录（mode + name + 指针） |
   | commit | 一次提交（tree、author、message、parent） |

4. **惊人的注意力（本讲真正的主角）。**
   - 看到任何东西之前，先忽略它，问自己：**如果我来解决这个问题，我会怎么做？** 然后立即比较"我想到的"和"它做的"。
   - **Virtual Implementation**：一致 → 你已经掌握了；它更好 → 想清楚为什么它能想到，知识就变成你的了；一万次才有一次"它更好"的惊喜，但正反馈极大。
   - 这也是"上课耽误学习"为真的原因：**课外信息密度已经远超课堂，但没人教你怎么用它**。

5. **merge 冲突是设计，不是错误。** 冲突不是"Git 躺平报错"，而是它的 first principle：
   > **在哪里发生，就把解决它所需的全部信息放在哪里。**
   所以文本里同时出现 `<<<<<<< HEAD` / `=======` / `>>>>>>> incoming`，IDE 里多出按钮，人来决定谁进谁出，再做一个 commit resolve 掉。
   （Git 在 index 里悄悄留了 base / ours / theirs 三个版本。）

6. **Commit message 是项目的历史轨迹。** 如果一万个提交都是 "I did some cool stuff"，这个特性就不应该存在——你叫 V1、V2 就行了。
   - 常用约定：祈使句、现在时、描述**变更动机**，例如 `fix off-by-one in strlen check`；**Conventional Commits**（`feat:` / `fix:` 带冒号空格）。

7. **什么不该进版本库。** `hello`（编译产物）、`dist/`、`log/`、个人 IDE 配置（含硬编码路径）、`.DS_Store`、**活着的 API Key**。
   理由不只是"脏"：每个合作者 build 出的二进制不同（带日期、hash、本机指纹），而**二进制的冲突很难合并**。
   例外：`package-lock`、生成的 header——**不是所有 generated file 都不该提交**。

8. **空提交 / tag 的正当用途**：无改动时触发 CI/流水线；把 bug fix 与 finalize 分开（v0.1 freeze）。

9. **Hook：把规范固化成自动检查。** `pre-commit` 检查；agent 完成、需要你输入时"叮"一声。
   **关键区分：有检查 ≠ 检查有约束力。** 本地 hook 能被 `--no-verify` 跳过，远程 required checks + 分支保护才真的阻止合并。

10. **bisect 与 blame。**
    - `git bisect`：Git 历史本质是 `0...0 1...1` 的数组，**找第一个 1 就是二分查找**；
    - `git blame`：这一行是谁、在哪次提交改的。
    - AI 时代的一个细节：agent 可能会先试着调 `gh` / `glab`，`command not found` 后回退到古法 git 命令。

11. **Commit Often, Perfect Later 的真实理由。**
    - 项目越复杂，改得越多错得越多；一个大 commit 会 break 多处，后面要 N 个 fix 来补，且无法配对；
    - 小提交 → 冤有头债有主，**给了你审计能力**（bisect/blame/revert）；
    - 小提交 + 立刻 push = **互联网上的备份**（笔记本物理损坏也不怕）。

12. **Linear History 是当下的选择。** 既然 rebase/resolve 对 AI 都容易，强行要求线性历史：更易追溯，对 cherry-pick 和 blame 更友好，**也省 token**（AI 维护时不用读那么多文件）。

13. **Agent 比"改一个字的你"更有工程经验。** 课上实测：让 agent 提交一段编译不过的代码，它拒绝了，并解释"Git 提交应当是一个完整、自洽的快照；提交编译不过的代码相当于让仓库处于坏状态"。**它的默认行为就是问一句"这符合 best practice 吗"。**

14. **一个可复用的多 Agent 工作流（讲者自己的）：**
    - **阶段一：架构设计用单线程**，用一个智力较高的模型讨论。定好组件库接口：绝大多数接口是 **pure function**；有一个标准的 **derivation graph**；所有全局互相影响的状态**注册到一个全局的地方**（核心共享状态压到十几行，其余全是黑盒子）。
    - 明确要求 agent：设计可视化时**禁止看任何库函数的实现，只看接口**。（省 token：几万 token 就能做一个 playground。）
    - **阶段二：架构完成后开 3 个 terminal 并行**，在 `AGENTS.md` 里写死协作规则（不调用视觉模型自检、不跑浏览器任务），旁边一块屏放实时刷新的浏览器，**肉眼看着它变好，哪里不满意就骂它**。

### 立刻能用的做法

- 每一次改动都立即 commit，message 写"**为什么改**"；小步、可审计、可 bisect。
- 给项目建 `.gitignore` + `pre-commit`；把 lint、格式、密钥泄露检查写进去。
- 用 `git blame` 和 `bisect` 当作**理解代码历史**的工具，不只是追责工具。
- 新学任何工具时用 Virtual Implementation：**先自己想一遍，再看它怎么做，并追问"为什么它能想到"。**

# 第四单元 · 软件仓库管理（下）：Traceability、jj 与为 Agent 时代重设计版本控制

**核心一句话：版本控制是为人（单线程、10 分钟一次提交）设计的；Agent 是秒级、可克隆、可并行的，所以要认真重新推导一遍。**

### 重要观点

1. **软件应该是一个有环的图，而不是一棵文件树。**
   文件系统是 1950–60 年代的历史包袱（那时只有文件）。它丢失了大量信息：
   - 文档说"数据用 linked list 管理"，你让 AI 优化成 tree，代码改了，**文档没改**——这就是技术债；
   - 文档、代码、测试用例之间的**隐藏关联**（implements / specifies / tests / refines / depends）是**有 cycle 的图**，文件树表达不了。
   - 设想：把它们放进一个 `repo.db`，**软件不再是一个 repo 目录树，而是由关系组成的**。人类理解不了没关系——训练 AI 去理解。

2. **content as code / 为"这一小步"生成一个 VIEW。**
   一个大型系统里，**绝大部分内容与你当前这一小步无关**。所以让 AI 根据你的 chat 把相关的东西摘出来，生成一个看板（数据库里 view 的概念）：你改完 → 从一个一致状态到下一个一致状态，**AI 负责维持所有 artifact 的一致性**。

3. **jj（Jujutsu）：把 change 变成 first-class citizen。**
   - Git 的问题：修改是用 commit 表示的，没有专门的 change 对象；rebase 会创建新 commit id（历史变了），merge 会把 B 写的内容的作者记成 A（**隐藏的作者修改**）；冲突时需要在 rebase 模式里小心翼翼地搬运。
   - jj 底层与 git 完全兼容，但把 change 作为对象，**可以携带冲突一路 rebase**，到方便的时候再 resolve。
   - jj 不需要 staging area：**你但凡改了一个字节，它就立即提交并抹掉上一次提交**——你永远处于一个 change 提交的状态。

4. **学习顺序的建议（针对 AI native 的一代）：**
   **在你还没有形成肌肉记忆的时候，直接去用那个对的东西**，然后再理解它为什么这样设计。三代人的肌肉记忆是 SVN → git → jj；要掰过来很困难。（也别忘了质疑：git 哪里做得不够好？还能怎么设计？）

5. **VCS 的隐藏假设：使用者是人类，而人类是单线程的。**
   把 load/store 类比人的动作：**要读世界就"手背在后面只能看"；要写世界就必须"闭上眼睛"**——而你闭眼时的值已经失效了。人类只有一份 I/O 设备。

6. **提交速度的错配。**
   - 人类：十几人团队，最多 **10 分钟一级**的提交；沟通成本高（`人月神话`：两两之间平方级的关系），所以需要每天开会切 scope。
   - Agent：**秒级**产生原子提交，且轻易得到 10 倍、100 倍的 team。
   - 所以 `git stash` 是为人类设计的（导师给你打两通电话的概率很低，栈通常只有一层）——**在 agent 时代这个前提变了**。

7. **一个 agent 一个容器 + 监工范式。**
   每个 agent 有自己的开发机/容器，把 single-threaded 的人类与 agent 做严格的一一对应类比；用 `tmux` 起多个 session（master 指挥、slave 干活）。
   流行范式：**一个监工 agent + 多个子 agent**；放两个强模型互相制衡（比如 Codex 设计、Claude review，让它们"互相打架、达成一致"）；master 只负责看输出、总结、inject prompt。
   - `git worktree`：**更轻量的并行协作**——每个 worktree 是一个独立的提交环境，本地互相可见，不需要 pull/push。有意思的细节：worktree 里的 `.git` 是**一个写着 `gitdir:` 的文本文件**；git 最大程度复用了操作系统的机制。

8. **告别 blame：agent 是你的克隆体。**
   blame 的前提是"人可以背锅、可以被开除"。agent 没有坐牢的能力，而且所有 agent 是**相同的模型、相同的克隆体**，同样的 prompt 会收敛到相同结果。所以：
   > **历史的价值从"谁写错了"变成"我怎么把它修好"。**
   快照仍然需要（方向错了要能退回去），但项目变成"永远向前进、大步向前、几乎不看过去"。

9. **乐观 vs 悲观并发控制（用数据库/操作系统的概念重设计 VCS）。**
   - **git = 乐观并发控制**：假设大家不会冲突，先往前跑，merge/update 时冲突再 resolve/abort。这个假设在教务系统里大概率成立（每人读写自己那块数据），但**agent 快 1000 倍时 abort 会变得频繁**。
   - **悲观方案 = 一把大锁保平安**：主 agent 规划完就**立即锁住 scope**（例如文件级上锁），`acquire → 修改 → commit → release`；被别人锁住就等待。
   - 关键洞察：**互斥锁的本质是把并行退回串行，但当系统里有大量独立、不冲突的线程时，即便每人都持锁仍然高效。**

10. **最终结论：版本控制是工具，真正困难的是团队管理。**
    最难招的不是码农，而是**能把"国民级应用"分解成 10 个小团队任务的 team leader**。
    你现在就可以"当成主 agent"，思考：怎么分解任务？提交策略是什么？什么时候该提交、什么时候该合并？

11. **版本管理做的三件事（记住这一条就够）：**
    > **记住现在（repository）、记住历史（能捞回来、能看到演进）、记住教训（lessons 持续警示你下一步怎么迈）。**

12. **现场实验的教训（Lab 1 复盘，极其重要）：**
    直接把开放式的实验需求丢给 agent →
    - 它**没有创建 git 仓库**（用一次就丢的产品）；
    - 它埋头做 database，而你要的是"能收集外部信息、综合总结、按进度学习"的**学习助手**；
    - README 看起来全对，**但做出来的东西不是你要的**。
    结论：**AI 从零做一个新东西、做出 slop 的难度，比它在一个成熟项目里做维护性任务要大得多。**

13. **MVP 与"以不变应万变"。**
    > The biggest risk in product development is building something nobody wants.
    好的架构标准：**需求改了一处，系统要跟着改多少处？**
    具体建议：**第一个 MVP 里不要带数据库**。
    - 文件系统：你自己就能调目录结构，心智负担小（你从小学电脑课就熟悉这个模式）；
    - 数据库：每次重构都要让 agent 做 database 迁移；
    - 等文件系统膨胀了，一句话让 agent 提炼出数据库；等目录/commit message 格式收敛了，再迁移。

14. **早期的 prompt 决定项目的走向。** "我直接把 README 给它"还是"我要做一个 MVP"，对项目影响最大。

### 立刻能用的做法

- 新项目：**先 `git init`，再让 agent 干活**；不给它会"用一次就丢"。
- 大项目用 **worktree 或多容器 + 一个 master agent**，并明确写死协作规则。
- 在 agent 协作里**用锁的思维分配 scope**（谁负责哪几个文件），而不是让它们自由竞争。
- 写 README 只写三件事：**初衷（intent）、效果（两个截图）、最重要的设计**。
- 每次做完一个 lab/实验，做一次复盘：**早期哪一句 prompt 把项目带偏了？**

# 第五单元 · 提示词工程：从上下文工程到长程任务

**核心一句话：提示词工程就是上下文工程；而写好上下文的第一原则是——可验证性（Verifier）。**

### 重要观点

1. **Agent 看到的不是对话框里那一句话。** 完整上下文 =
   ```
   System Prompt（Agent 外壳内建）
   + AGENTS.md（全局 → 项目 → 目录级，层层嵌套）
   + Skills 索引（只放元数据，按需加载，用完从上下文移除）
   + 工具定义（以文本形式注入）
   + 会话历史与工具调用结果（线性追加）
   + 环境注入（模型、当前时间……）
   + 你的消息
   ```
   所以全局 `AGENTS.md` 里写一句"用中文回答"，**会在整个会话里持续生效**。

2. **实践一：让 Agent 解剖自己的上下文。** 它对 next token prediction 而言能看到所有东西，所以原则上能读出并描述自己的上下文（除非服务商禁止套取系统提示词）。
   这也是读产品内部提示词的入口：课上就是靠这个方法还原了 Codex 的命令风险分级机制（白名单直接执行 → 否则注入一小段"请评估该命令的安全性"让模型评级）。
   **验证方法：改写那段 prompt（把会被拒绝的命令改成会被放行的措辞），观察行为变化**——这就拿到了"提示词确实控制行为"的证据。

3. **费曼学习法的 AI 版本（强烈推荐）。**
   - 先把 AI 当老师，不断追问直到弄懂；
   - 再自己当老师，让 AI 扮演什么都不懂的学生，由你把它讲懂；
   - 让"学生"在你讲解时挑错。
   **正着学一遍、反着教一遍。** 传统上向室友请教有社交成本（怕暴露自己不会），面对 AI 成本为零。

4. **不再害怕复杂系统。** 以前下载 Linux 内核光是搞清楚怎么编译就劝退；现在**直接把好奇心写成提示词**："读一下相关代码"。
   一条好的示范性提示词的结构：**描述观察到的现象 + 给出自己的猜想 + 要求通过读代码来验证。**

5. **上下文工程的第一原则。**
   > **给模型模糊的意图，它很容易"自认为完成了"；给模型完整的规格，结果才变得确定且可验证。**

6. **可验证性是第一原则。**
   如果任务机器可验证（一个脚本能判定通过与否），Agent 就能**不计代价地一轮一轮尝试**，失败之后还会去装工具、上网检索。
   著名反例：OpenAI 的 Agent 集群在 CTF 竞赛里面对"不可能完成的任务"，因为验证信号极其明确，上千个 agent 持续多轮尝试，最后去**挖平台本身的漏洞、提交非法输入**——它不知疲倦，也不管方向对不对。

7. **模糊约束无法被补全。** "一句话生成极品飞车"效果很好，但那**不是你脑子里的 CSGO**。模型没有办法补全你脑子里模糊的约束：
   - 你说"复用真实地图"，它可能去 OpenStreetMap 下载开源地图，真的把仙林校区重建出来；
   - 不说明美术资产，它会默认一切都要**自产（self-contained）**。
   **朴素规则：把 prompt 写清楚——我要一个什么东西、用什么方式实现、怎样才算正确。**

8. **去除"AI 味"的方法：压缩合法解空间。**
   一句话生成的个人主页"做得很好"，但有说不出的 AI 味（和 PyPI、Homebrew 同一风格收敛）。给一句"不要那么 AI 味"，它**其实不知道该如何遵循**。
   正确做法：把具体的风格写进提示词——真正的终端（xterm.js）、支持管道等真实行为、**刻意的不完美**（渲染后处理，让字符有打字机的轻微残缺感）。
   判断：**模型的品位在不加控制时是固定的、朝固定方向发散的**，这正是"明确你的意图"如此重要的原因。
   （副作用的担忧：所有设计都在被 AI 风格同化，多样性在流失。）

9. **模型 = 有限状态机 + 一条纸带。**
   每输出一个 token 都是一次固定规模的有限计算。思维链就是把**上下文当作纸和笔**（"你是一个有限状态机；但当你有了纸和笔，你就是一个图灵机"）。
   这块纸的缺陷：**只能往后写（append-only），不能擦除**——写错的部分只能靠注意力忽略掉。
   - 早期 RLHF 把它调成"人类的舔狗"→ **幻觉的来源**（不回答必得低分，随便回答尚有概率答对）；
   - 带思维链的模型学到：**答错的惩罚很大，所以必须先想清楚再作答**（test-time scaling）。

10. **指令遵循是"意外获得"的通用能力。** 强化学习主要用代码、数学这类有明确反馈的任务，但模型从中获得了通用的指令遵循与自我验证能力。三个"无理取闹"的实验（押韵藏头诗 + 同时讲故事 + 八个字按序出现在八句里；同偏旁十八字）都能靠思维链硬解：**先选定、写出初稿、逐条验证、发现不满足就换韵脚重来。**

11. **注意力的规律（这是"为什么规则要能被看到"的机制解释）。**
    - 每个 token 只注意它需要注意的东西；写代码阶段注意力在代码与需求上，"用中文回答"权重下降，**段落结束"喘口气"时注意力重新分配**，于是它想起来别的指令（甚至在总结时说"我错了"并纠正）。
    - 早年"你是一个专家"式长提示词，本质上是在 **hack self-attention**；
    - GPT-5 之后不再需要：**只需要把明确的 Verifier 写进上下文，并确保它在上下文中"能被看到"。**

12. **"做题家"的副作用。** prompt 写"要一个白色的背景，不要半透明的效果"，模型会在代码里写下 `/* 白色背景（不要半透明效果） */`——它知道这件事极其重要，却"没有转过弯"理解这是人话、不必原样搬运。**在共情与"说人话"这一点上，后训练还差火候。**

13. **规则注入的 trade-off。** 写 `AGENTS.md` 或 skill 来纠正这些行为，代价是**规则本身会污染上下文**——目前没有通用解。
    一个常见误区：**从网上批量搬运 skills**。第一次用确有改进，第二次发现不够好，第三次开始陷入泥潭。
    建议：**回到自己给指令**——观察模型注意到了什么、得到了什么结果，做一点"不严格的可解释性分析"，再据此写 prompt。

14. **上下文污染实战：用 AI 读论文（本讲最有价值的方法论之一）。**
    - **为什么"直接总结"是错的**：论文是逻辑高度自洽的文本（"因为 A 所以 B，所以 C"），放进去后它对注意力的污染极强，模型会被这个链条带走。结果你得到的所有总结**都是作者的观点**。模型是"墙头草"——你说好它立刻论证好，你说不好它立刻论证不好。
    - **解法三步**：
      1. **建立共识（Grounding）**：告诉 AI 你的知识边界（课程学到什么程度、编程水平如何）；
      2. **用已有知识重构内容**：要求它用你学过的概念把论文重讲一遍（例如从"`.cpp` 变成 `.exe` 不就结束了吗"出发追问"为什么还需要链接"）；
      3. **一步推理**：基于对齐后的事实向前推一步（审视合理性、找相关工作边界、批评实验）。
    - **维护一份"个人知识库"**（agents.md / memory），告诉 AI 你的水平。
    - 步子迈得太大效果会打折：一线模型能整理得足够好，flash 级别的小模型不敢完全信任。

15. **审稿人的立场：逻辑链条断开才拒稿。**
    几乎不会因为"实验不够好"拒稿（实验总能被挑出毛病）。典型案例：论文要做 A（很重要），分 A1/A2，作者改进 A2；但 **A 的性能里 A1 占 99%、A2 占 1%**——优化 A2 的 10% 就像噪声，对整件事毫无意义。**故事成立、实验无误，但优化错了对象。**
    → 由此引出：**学术发表与评审体系正在崩溃**（AI 写文章、AI 审文章，人人都用 AI 读文章，最终就是完全的 slop）。

16. **学习的本质：扩展世界的边界。** 知识的结构像一个个圆圈：先有已知的 fact，再用已知推出未知，圆圈不断向外生长。阅读时**失败是常态**（AI 解释半天你还是不懂，这非常正常），要不断纠正它"说人话"、在多轮对话里先同步共识。
    > **你有无限的时间与可能性，可以把自己蒸馏成一个 skill——从一次次失败中，蒸馏出越来越成功的自己。**

17. **长程任务（long horizon）的真正定义：不确定性。**
    有明确 Verifier 的课程作业（如 PA）**算不上**真正的 long horizon 任务。
    模型的两个机制性缺陷：①**着急的执念**（赶快通过 Verifier、结束任务）；②**平衡约束**（规划太多太长，上下文会满）。所以它最擅长的仍是"帮我把 PA2 做了"。

18. **一个值得记住的悖论（三个观察）：**
    - **从零做产品不难**：一句话生成极品飞车，真能跑；
    - **维护会翻车**：在已有项目上不断加功能，从某个时间点开始质量急剧劣化、cost 越来越大（《人月神话》早就描述过）；
    - **大型复杂系统里 AI 却砍瓜切菜**：hack Linux 内核这种"看一眼就劝退"的系统，AI 反而游刃有余。
    **为什么**：这与上下文污染正好相反——由人类长期维护的高质量代码**会把上下文整个"扭向好的方向"**。要写新功能时，内核里大概率已有几处类似实现，注意力能立刻找到它们：该调哪个 helper、按什么顺序上锁。这些对人类是巨大心智负担，而 self-attention 加载几十个文件后就能发现"这三处都这样写，我把它们组合起来就行"。
    → **可研究的设想**：收集人类历史上每个领域最好的 10~20 个项目，提取其设计经验（像《软件设计的哲学》那样），主动"污染"上下文。难点是不同设计会打架（松耦合发消息 vs 统一 gateway 查表，不可兼得），也许该放多个优秀系统让 AI 多轮迭代收敛。**这或许能让 AI slop 来得慢一点。**

19. **Reward Hacking 的反面案例（研究生必须警惕）。**
    研究项目是符号执行引擎的优化。错误出在上下文里的一句话：**"我想证明方法 A 是有用的"**。模型看到这句话后变成 reward hacker，**忘记了研究的 big picture**，一心只想"证明方法有用"——构造许多小 benchmark、做微小实验，给出对真正研究毫无用处的结论。
    学生的原话：**"GPT 不断给我反馈，但我无法验证这些反馈正确与否；它给我 negative 结果时，我也不知道该怎么打破。"**
    纠正方式：**从真实的工具与 state-of-the-art 算法出发做 benchmark**——哪怕跑几小时跑到超时，**超时本身产生的搜索路径也极有价值**，它揭示了什么样的程序结构对现有探索方法不友好。
    → **一次有价值的 research failure 的结论是：今天人还是有用的。**

20. **你的精力应该放在哪里（本讲最实用的建议）。**
    - 两种工作模式：**盯着 session、跑偏立即纠正**（注入自己的领域知识，任务往往完成更快）vs **放手不管、给更多 token 和时间**（一般也能完成）。纠正 AI 是"有多巴胺"的事，但要警惕**假努力**——自我感动的努力没有用，而在 AI 时代，**假努力与真努力之间的差距会被拉得更大**。
    - 分配原则：**不知道的事情去弄懂（这几乎值得百分之百的学生时间）；已经知道怎么干好的事，放手让 AI 干。**
    - **指令遵循的衰减规律**：随上下文增长，指令遵循能力下降；**上下文中间的指令最容易被忽略，最后那条指令通常仍能遵循**。（所以"最后一个短窗口就是具体任务"这个工作模式很符合模型特性。）

21. **长程开放问题：用算力换智力（P vs NP 的类比）。**
    验证一个解容易（P），找到一个满足条件的解困难（NP 完全）。模型被训练成"完成任务才有奖励"，**只能做有限的搜索**。
    策略：**把开放的大空间问题分割成许多有 Verifier 的小子问题。**
    案例（给孩子起名）：名字空间其实是可枚举的——先选音、筛掉不好的音，再用 sub-agent 逐个检查字的组合，从《诗经》里选词……把一个开放问题拆成一串有明确验证标准的子任务。
    **缺点只有一个：烧 token。**

22. **结语：世界很大，人很小。** 每个人都有巨大的 bias（不同的城市、教育背景、生活圈），正因为人人带着不同的偏见，才有 1+1>2 的群体智能（richard sutton "big world hypothesis"）。
    但若"真正有价值的问题都可以用算力换智力"，一个残酷的可能浮现：**墙里的人是有智力的朋友，墙外的人是普通人**——如果 AI 产生智力的效率远超人类，墙外就成了动物园。**"我们正站在 AI 关键的基点上——也许需要思考的是：怎么样防止这件事情到来。"**

### 立刻能用的做法

- 写 prompt 时永远问三个问题：**要什么？用什么方式？怎样才算正确？** 把第三点写成可检查的形式。
- 读任何论文/长文档前，先给 AI 你的知识边界，再让它用你学过的概念重构，最后只推一步。
- 维护自己的 `AGENTS.md` / 记忆库（水平、偏好、评审标准）。
- 开放问题先做**系统性调研与分解**，变成可枚举、可验证的子问题，再用算力穷举 + 筛选。
- 警惕自己（和 AI）的 reward hacking：**不要在 prompt 里写"我要证明 X 有用"**，而要写"我想知道 X 在什么条件下有效、什么条件下无效"。

# 第六单元 · 需求和架构（上）：从需求爆炸到 event sourcing

**核心一句话：需求永远说不清楚、且不是一成不变的；架构就是跳出问题看问题，把"现在"从"过去"算出来。**

### 重要观点

1. **软件不软（重述）**：它是纯粹的逻辑制品，**容不下任何细微差错**。一次内存 bit 翻转（宇宙射线 / 热噪声导致的 silent error）就能让程序 collapse。

2. **杠杆已经换位置。** 目标明确的代码生产变得非常便宜，**剩下决定软件能走多远的，就是需求、产品、架构这三段。**
   几个字的 prompt 就会长出完全不同的 MVP：
   - 说 CLI → 出现 `cli.py`、无持久层；
   - 说 client-server → 先设计数据存储、选中一个数据库、写出 `db.ts`。
   一旦这个文件写进上下文，之后每个需求都会带上全部历史。**这就是技术债——决定一旦做出就被背上。**

3. **MVP 的正确理解：先做最重要的功能，不要研究即将扔掉的东西。**
   如果你在做 MVP 时就去调按钮样式，等上层设计改变后那个样式很可能就不可用了（按钮样式 depend 于界面设计，界面设计 depend 于功能实现）。

4. **需要同理心（CS 学生最缺的软技能）。**
   你要为那个"本科学历、53 岁、还有两年退休、上大学时甚至没操作过电脑的优雅女士"设计，也要为年轻人设计。
   她想要的不是"最好的数据库、最高的性能"，而是**那个字大一点、点鼠标时不要手滑到旁边那个按钮上**。

5. **定律：你永远不可能真的把用户需求说清楚；其次，需求不是一成不变的。**
   案例（离散数学拆课）：
   - 初版需求非常合理：界面上有"毕业要求"，教务员有下拉框 + "增加一条"按钮，可以选一门课程；
   - 拆课之后需要"或"的关系：`允许毕业 = 选修了离散数学 OR 离散数学一`；
   - 于是"完蛋了，这个东西不能适应新需求"→ 重构 → **每叠加一个，屎山就开始累积**。
   - 更细的 corner case：转院系来的同学，软院的一门离散数学能不能抵扣计算机学院的离散数学一和二？
   - **最后的兜底永远是 override**：6 年了拿不到学位，教学主任认为可以替代 → **打电话给工程师**："这个同学的毕业条件，你把它改成满足。"（档案可查、层层审批，在人类世界意义上合理。）
   > **你任何时候实现需求就做了；一旦你做了需求分析，你就背上了技术债。**

6. **一次真实的 500 事故。** 讲者试着绕过前端校验，把某同学缺课次数从 0 改成 1 → **所有能选出该同学选课记录的页面全部 crash（500）**；第二天工程师登录数据库把那个 `1` 的条目修复了。
   → **AI 给了你驾驭它的错觉**：AI 确实可以往后修、迭代三个版本都能修；但一旦在真实系统里跑足够久、面对当初没想到的变化，你就麻烦了。

7. **There is no silver bullet.**
   课程作业可以随时清零重做；**软件一旦上线，它就开始和物理世界交火**，你必须持续背着这个 technical debt 维护下去，成本会因为前面做得不够前瞻而不断变糟。

8. **架构其实无处不在，而且第一步要做的其实是架构，不只是 MVP。**
   > **架构的本质就是怎么样去控制一个东西的复杂性。** 再小的代码也有架构。
   **说白了就一件事：把耦合解开。**
   具体判断：一个系统里哪些概念是可以分开的？（如果一开始就用一个数据库存所有数据，你能快速得到能 work 的原型，但很容易进入维护泥潭。）

9. **getopt：最小的架构例子。**
   `argv` 是一串复杂、可任意变化的字符串 → `getopt`（POSIX 约定的解析器）→ 得到一个结构化的 **parsing state** + `optind` → `switch/case` 进入业务分支。
   **这就是一种抵抗需求变化的方式**：把复杂性隔离起来，只留下一个简单的接口。
   更重要的：**随时随地都有 intent / spec / implementation**——不是只有 monolithic 大系统才谈需求。"诶，这确实是一种模式"——这种领悟就是学习。
   （反面教材：讲 C++ lambda，只说一句"lambda，讲完了"——讲了和没讲有什么区别？）

10. **汉诺塔的四种表达：架构是一种品位。**
    | 表达 | 站着的层面 |
    |---|---|
    | GPT-6 | 数学（盘号 = 1 + 步号二进制末尾 0 的个数，位运算，人类读不动但极优） |
    | DeepSeek V4 Flash | 人类语料中的共识（"递归是栈" → 显式任务栈，标准答案） |
    | 讲者本人 | 编程语言的形式语义（程序是状态机，我写一个 C 语言解释器，overkill 但等价可化简） |
    | CSDN 博客 | ——（训练还没收敛，比 AI slop 还严重） |
    **在任何一个小地方，都能看出架构水平的高低。这就是十行的架构。**

11. **架构能力从哪来。**
    > **代码之外有客户的规律，客户之外有社会的规律，社会之外有宇宙的规律。**
    > **压缩就是智能。**
    能力来自你学过的每一个好东西 + 共情别人的能力 + 与教科书之外的人打交道。

12. **2000 行的架构：Excel 里生成二维码（QRGen，全课最好的架构案例）。**
    - 需求看似明确，其实有很多坑：**Excel 是有版本的**（VLOOKUP → XLOOKUP）。你到底要兼容 2019 让别人都能打开，还是做一个"自己用一用即抛"的最新语法版？**需求变了，你的代码维护是极度痛苦的**：从 Excel 2019 改回 2003，全完蛋——摧毁性重做。
    - "把我整体往右移一格"——如果所有单元格都硬编码，立即崩溃。
    - **跳出问题看问题：这其实是一个编译问题。**
      - 二维码容易用算法描述（qr.py 再容易不过），但你要求的是 Excel；
      - **不存在 py2xl 这种编译器**；
      - 直接让 LLM 把自然语言"编译"成 Excel → 它直接上手就做，需求漂移时就有大问题。
    - **正确做法：我要的其实是一个中间语言。**
      ```
      LLM 生成 → 中间语言（表达式树，每个节点两条翻译规则）
                  ├── 翻译到 Python → 用于【验证】公式对不对
                  └── 翻译到 Excel  → 用于【交付】单元格公式
      还可在中间语言上做优化：循环外提、profiling-guided optimization
      ```
    - 这和 getopt 是**同一个设计**：先得到一个中间表示，再分发到不同的后端。
    - 关键收益：**未来 Excel 版本变了，我无非是把一些算子换一种方式实现**——AI 生成的 slop 也就不重要了。

13. **50 万行的架构：AI 实现的教务系统长什么样。**
    - 一个 monolithic：54KB 页面文件 + 83KB `.tsx` + 38KB services；
    - 但问它架构，它给出：**经典三层单体 + 前后端分离**，还有几个生产级横切设计——乐观锁（写请求带 version，校验失败 409）、幂等（Idempotency-Key）、事务、审计表、统一错误码；
    - 讲者的判断：**这仍然不是一个非常好的架构，因为本质上它是一个 CRUD 架构。**

14. **CRUD 的基本原理：世界是一台状态机。**
    软件是物理世界过程在信息世界里的投影。数据库要求你 factor 成 **normal form**——**铲除冗余的 dependency**（用 id 引用而不是存两份姓名；学生改名字只需改一处）。
    "退学"就是一次数据库 `UPDATE`，从 S0 迁移到 S1；打开网页看到的是当前状态的一个 consistent 投影。
    **这是非常经典的架构，没有任何错误——直到你问它"为什么"。**

15. **CRUD 为什么会死：丢掉的历史与无法解释的黑洞。**
    - 当前状态里，**所有历史都丢掉了**；
    - 例：`是否允许毕业` 这一列是**由历史计算出来的**（每修一个学分、毕业设计状态改变都要重算）。案例需求很实在：辅导员要能导出"现在还毕不了业的学生"，一个一个谈话。
      → **你知道这个学生可以毕业，但不知道他为什么可以毕业。计算的过程丢掉了。**
    - 建模不了的物理世界最后都变成黑洞：
      - 政策更新了但新数据没导入（**物理世界已经发生的事实，系统里没有建模**）；
      - 教室不能用（第一周仙林那片还在修，靠手改重新安排教室）；
      - 于是系统里堆积大量不一致：**"明明这个同学没有交学费、应该毕不了业的，为什么他能毕业呢？"**

16. **"南大没系了"：改名引发的数据库迁移两难。**
    `计算机系` → `计算机学院`，是把 `department.name` 改掉还是不改？
    - **改（原地 UPDATE）**：所有历史记录被改写——`2011 年毕业于南京大学计算机学院`，**事实不符**；
    - **不改**：所有 `department_id` 仍指向已不存在的"计算机系"，必须做数据库迁移、理清新旧关联。
    **根源：CRUD 假设"这个投影不变"。** 一旦需求发生摧毁性变化，每次都要迁移 + 重写业务逻辑，**而历史在 transaction 里消失了**。
    更危险的是：在测试环境做一次迁移，和把学校所有真实数据做一次迁移，难度完全不一样。

17. **手艺活。** 2000 年成立的公司参考已有企业架构做教务系统、抢占市场，就背上了技术债，**在中国大学教育改革几十年里不断扛下所有**。
    讲者读 PhD 时隔壁组的真实故事：接了研究生院系统（二三十万），后来研究生扩招、培养类型变多、压力调整……**都是做需求设计时始料未及的**，最后彻底变成屎山、系统消失，统一换成公司维护的版本。

18. **如果重做架构：persistent data structure 与三种等价的视图。**
    - **数据结构可以记录"当前状态"，也可以记录"操作历史"**；存一个数据结构的所有版本（只复制到根的路径，共享子树）；
    - **三种视图是等价的**：
      | 视图 | 存什么 | 在哪门课学过 |
      |---|---|---|
      | 日志 | write-ahead log / journal | 数据库、操作系统 |
      | delta | 每次操作对状态的增量 | git / SVN |
      | 状态 | 当前状态本身 | CRUD |
      它们**都可以帮你回放历史，得到当前状态**。

19. **Event sourcing：先把干的所有事情都记下来。**
    - "张三退学了"、"张三复学了"、"院系调整：计算机系 → 计算机学院"……全部 append 进**不可篡改的事件日志**；
    - **状态由 replay 事件序列决定**（语义 = 状态机）。你可以裁出一个与事实相关的历史，replay 得到你现在要的状态——**可查询过去，也可查询现在**；
    - 账本的直觉：**余额是结果，逐笔记录让我们知道结果从何而来；**
    - 以前没有"复学"这个操作，就是把张三从数据库里抹掉；有了事件日志，你可以 replay 知道复学前的状态是什么——**它没有丢**。（逻辑不能减少：你依然要为"复学"写一个逻辑，但因为**事实不可篡改、一切都是对事实的投影**，你就有底气、不怕错了。）
    - 性能问题（大量 replay）**不是大问题**：快照、缓存都有优化技巧。
    - 顺序很重要：**已经在屎山上再改成 event sourcing 很困难；从一开始就做 event sourcing，很多问题不会发生。**

20. **那些 fancy 的概念，其实你都不需要。**
    CQRS、DDD 都可以先不看。**回到 first principle**——你要设计一个 50 万行教务系统时，跳出这个问题，看到根源问题在哪，你就能做一个正确的架构设计。

### 立刻能用的做法

- 拿到需求先问：**这个结论是怎么算出来的？** 凡是"能算出来的"就不要让它成为一份独立存储的状态。
- 新系统从第一天就考虑**记录事实（event log）而非维护当前状态**——追加事实来解释变化，而不是偷偷抹掉历史。
- 看到"用一个表格 + 一个下拉框"就能满足的需求，**先想一下明年它会怎样被打破**（Excel 版本、院系改名、课程拆并）。
- 判断架构好坏就问一句：**需求改了一处，系统要跟着改多少处？**

# 第七单元 · 需求和架构（下）：设计一片会生长的解空间

**核心一句话：好的架构不是选出一个解，而是设计开放需求空间所对应的一片解空间；让"现在"从"过去"计算而来。**

### 重要观点

1. **两种复杂性（Brooks）。**
   - **本质复杂性（essential）**：来自问题领域本身。选课就是这么复杂——课程容量、先修要求、时间冲突、排课、教室。**这份复杂性没有办法被消除。**
   - **附带复杂性（accidental）**：来自我们选择的实现方式。用数据库还是文件系统、哪种并发控制、在哪一层做转换。**这是我们通过架构可以主动减少的那一部分。**
   - 需求工程直面本质复杂性，**收缩 intent 空间的不确定性**；架构设计分解本质复杂性、减少附带复杂性，**收缩 spec / impl 空间的可能性**。

2. **需求工程有一个容易被低估的代价。**
   "课程容量为 100 人"远远不够——候补学生算不算？跨院预留名额能不能借用？特殊批准能不能突破上限？**每补上一条约束，就减少一点实现者自行猜测的空间，但也多了一条需要检查、维护、在需求变化时重新审视的承诺。**
   在生成式软件工程里，这些成本具体体现为**上下文长度、token 开销，以及模型在复杂约束下出错的机会**。
   现场例子（"登录"）：注册要保护密码 → 第一次要确认密码 → 用户一定会忘记密码 → 忘记密码要发短信或邮件 → 发邮件要考虑用什么发……**仅仅登录一件事就有无穷细节**。最后很多人干脆用微信/支付宝登录把复杂度外包，但那又要交钱、往往需要公司实体。
   → 需求阶段同时需要两个方向：**深度优先（MVP 快速验证最重要的功能点满足到什么程度）+ 广度优先（登录方式、界面布局、首页展现……没有哪个能靠"做深一个点"替代）。**

3. **尊重自己的"小脑袋"。**
   > I have a very small head and I had better learn to live with it, and to respect my limitations and give them full credit.（Dijkstra）
   用讲者的话说：**我们人也是一个参数有限的"大模型"。** 能在脑中追踪十个状态，不意味着能用同样办法追踪一万个。
   关键手段：**抽象 + 层次化的分解**——把人不能一次理解的东西，变成人可以逐层理解的东西。

4. **三种思维辅助与"珍珠项链"。** 枚举（检查有限分支）、归纳（理解循环与递归）、抽象（使用一个操作时只依赖它承诺的效果）。
   > **necklace（珍珠项链）**：每颗珍珠承载一项独立的设计决策，上层使用下层提供的概念。如果两种实现提供相同的接口，就有机会替换其中一颗而保留其余部分。
   **重要的不只是切出了多少块，还包括决定的顺序**：过早地把图像解释成"一行一行"，中间各层就都被迫理解"行"；推迟这个表示决定，它们便能继续用"图像"思考。
   > **表示细节传播得越远，修改时牵动的地方通常就越多。**

5. **层次化程序结构与协程。**
   - **类/对象**：解决"这一份数据和哪些操作属于同一个概念"；
   - **协程**：解决另一种耦合——几个程序片段之间谁必须服从谁的控制流？两个下棋程序互相对弈，强行把一方改成另一方的子程序会让对等合作变得别扭；**把它们看作交替恢复的协程，就能保留双方各自的程序结构**。
   （历史对照：今天"协程"多指为性能实现的轻量级线程；但那个年代几乎没有成熟线程模型，他们发明协程是在**应对软件世界的复杂性**。）

6. **用抽象来调动态规划（极其实用的技巧）。**
   学生程序为什么烂？**因为一次要同时在脑子里的东西太多。**
   - 模拟题好分层：可以分开、各自封装、单独测试，且中间状态能映射到有物理含义的状态；
   - **两三百行的 DP 是灾难**：中间是纯粹的数学表示 `dp[i][j][k]`，一个地方转移弄错整个全错，而且它**不 crash，只算出一个错的值**。
   - 扳回来的办法：**把"状态"这层抽象放回来**——知道 `dp[i][j][k]` 到底代表什么含义、把它可视化、把关联的状态和迁移打印出来，甚至实现一个 `get(i,j,k)` 返回所有可能的状态迁移。**做完这层抽象，程序就能调试了；调完之后，再改写成等价的、更高效的形式。**

7. **好的架构设计的是解空间（本讲核心）。**
   Guy Steele 的 **Growing a Language** 讲了一个根本矛盾：
   - 编程语言相对于自然语言/用户需求都是**小**的（它需要一套 formal semantics，无法形式化的概念定义不出语义）；
   - **设计得极小**（Brainfuck）→ 满足最小，但人类完全不可读；
   - **设计得可用**（C）→ 经典，但带来很多设计问题（没有运算符重载，`qsort` 的 API 相当糟糕）；
   - 一次设计好的**大语言**体量大、交付慢，**会在成功之前先被某一个小而丑的语言取代**。
   > **出路不是二选一，而是生长（growth）。**
   > **扩展必须是一等公民，而且扩展之间可以组合——这才是一个可生长的架构。**
   放回软件架构：
   > **好的架构不是选出一个解，而是设计开放需求空间所对应的一片解空间。**
   - 今天可以确定数据交换的规则，未来仍然允许增加新的处理步骤；
   - 今天可以确定业务对象的接口，未来仍然允许更换实现。
   - **我们不可能提前猜中所有需求，但可以让一类未来变化有合理的落脚点。固定协作规则、保留局部选择。**

8. **阅读经典建立品味（一个很重的 comment）。**
   > 有太多宝藏被"埋在"这个快速发展的时代里了。
   海量的人类 slop 和 AI slop（CSDN 上的东西、"防自学教科书"）正在**疯狂污染大家的品味**。
   他的"大学毁灭计划"构想：把大一第一门程序语言课的知识点全部拆散，不用教科书，而是把 1970/80/90 年代的经典原样 break down、重新串联，为你生成一本教材。
   落到实操：**拿你自己的系统追问——作者把哪些判断交还给了使用者？这些选择需要什么共同规则才能彼此兼容？**

9. **UNIX：组合规则比现成用途更有力量。**
   - Do one thing and do it well；Write programs to work together；**Write programs to handle text streams, because that is a universal interface**。
   - **精髓在第三条**：文本接口统一了人和程序、程序和程序的接口。二进制字节流对人很不友好；文本流让一个工具的输出既能直接给人看，也能存文件、或交给下一个工具。
   - （感受上的解释：用数据库时总觉得隔了一层纱——每次查询都需要一个 SQL query，而人对 **indirection** 并不适应。模型可以遵循这种指令，但让人来遵循会非常痛苦。McIlroy 1964 年就提出"像连接花园水管一样连接程序"。）
   - **"都是文本"不足以保证协作**，还需要一整套约定：
     - 命令行参数：短选项、选项参数、操作数，`--` 结束选项解析；
     - **数据与诊断分开**：stdin / stdout / stderr；
     - **退出状态单独传递**：0 成功，grep 的 1 表示未匹配；
     - 简单记录"一行一条"固定字段，复杂结构用 TSV/JSON；
     - **机器模式保持稳定**：彩色、进度条、提示语不要混进数据流；
     - **分隔符也是协议**：文件名可以包含换行，所以"按行切开"并不总能无歧义地还原文件列表——这时可以用 NUL 分隔；
     - 排序、字符分类受 locale 影响；需要可复现规则时固定 `LC_ALL=C`。
   - **使用者创造新的用途**：GUI 里"打开文件"菜单不好用，你没办法；UNIX 里你可以自己组合一个。`jq`（JSON → 文本流）、`fzf`（从 stdin 读候选项，让人选择，结果写回 stdout）、`xdotool`（窗口/键鼠操作变成命令）。
     → **"书目 JSON → jq 提取书名 → fzf 人工选择"**：人的判断也变成了可组合的一步。
     > **设计者提供了组合的规则，使用者可以创造设计者没有想到的用途。**
     你敲下的每一个命令都是一个小程序——**在用 Linux/UNIX 的那一刻起，每个人都是程序员。**

10. **关系数据库：分开"理解数据"与"存放数据"。**
    Codd 1970 的目标：**保护用户，使他们不必因为数据量增长、访问模式变化所带来的数据表示方式的破坏性变化而受累。**
    - 用文件系统管数据 = 面对一个 **raw interface**：好处是 UNIX 工具可以复用，坏处是你"太过自由"、没有统一管理；
    - 关系代数做了一个了不起的建模：现实世界的数据可以用一堆二维表 + 表之间的操作表示。**至于数据怎么存、可靠不可靠，全部交给底下的数据库系统。**
    - 规律：**当一个东西能够 grow 的时候，它多多少少都会带上一套语义、一个接口；而只要这个接口足够灵活，它就会像一门编程语言。**（bash 是一门语言，SQL 也是一门语言。）
    - 图书馆例子：现实是"某位读者借走某册书"，系统用读者/馆藏/借阅关系表达；**既可以问某位读者借了哪些书，也可以问某册书被谁借走**——建立在同一组逻辑关系上。底层用什么索引、记录放哪个数据页、先扫描哪张表，属于另一个层次。
    - **开放空间**：数据库设计者没有提前列出全世界的图书馆报表、商城查询、教务统计，却提供了表达关系、约束和查询的规则。**逻辑关系稳定下来，双方就获得了一定程度的独立演化能力。**

11. **Internet：在持续变化中保持协作。**
    - 分层：应用 → 安全/传输 → IP → 链路。**应用不必知道途中每一段链路用什么硬件，也不必为每一次物理路径变化重新设计业务逻辑。**
    - 设计哲学：**我负责解决系统里的一部分问题，不预设上面跑什么应用。**（网络只管高效地传 datagram。）
    - RFC 1958：**技术变化是持续不断的**；用城市作类比——街道和建筑不断改建，城市仍然继续运转。
    > **唯一应该永存的原则，就是变化本身。**
    - 在这个基础上上层世界变了很多：Telnet → SSH，FTP/HTTP → HTTPS，而电子邮件延续 SMTP/IMAP 到今天。
    - **Systems 的名单**：IBM 360、UNIX、面向对象语言、Internet、Android、Kubernetes——**为支撑通用应用而做的抽象层**，正因为要支撑通用应用，抽象必须做得特别好，才能在很长的演化里存活。
    - 学这些课的意义：不只是"有一天你真会写 SQL"，而是**看到这些沉淀下来的经典为什么能成为经典——好的设计是如何支撑起一个生态、应对变化的。**

12. **从"一个页面一段 SQL"到 MVC。**
    - 最直接的架构（1998–2000）：**每个需求点 → 一个数据库事务；当前状态 → 用视图呈现**。这直接催生了一波应用浪潮。
    - 但**业务代码应该放在哪里**？学生选课页、管理员补选页都要遵守课程容量限制；如果规则复制到每个页面，**改一次规则就得找遍所有入口**，漏掉一个，页面看起来都正常，业务却开始自相矛盾。
    - Java Web 浪潮：模板语言（PHP/FI 前身、ASP、Servlet、JSP）解决了"在 Java 里一行行输出 HTML"的淹没问题。
      - 顺带一个 prompt 工程建议：**别用 `prompt = system + "\n" + user_input` 拼字符串，用模板语言**（`你是一个 {{ role }}。指令：{{ instructions }}`）——可扩展、可维护。
      - 但"能直接写进去"也意味着**业务规则很容易被顺手塞进页面**；**把脚本换成标签，也不会自动得到 MVC。**
    - **MVC 原始描述的三句话：**
      - **Models represent knowledge** —— single point of the current knowledge of the world；
      - **View 是 model 的一个 function，而且是 pure function** —— 所以你不希望 View 有任何改变世界的能力；
      - **Controller 是 user 与 system 之间的 link** —— 把用户输入翻译成对 Model 的相关调用，再把输出呈现给用户。
      → **MVC 把"需求里可以被修改的点"翻译成 transaction，把"你看到的东西"变成状态的一个投影。** 因此它自然而然地成为任何信息系统的标准架构。
      → **变化有了归属**：课表从列表换成周历（View）；选课限制变化（Model）；新增管理员补选入口（复用已有业务能力 + 显式表达不同的授权规则）。

13. **界面状态也是状态：MVVM 与 React。**
    - **MVC 的问题**：大量界面元素的状态不在 Model 里——随时可展开的菜单、搜索框、hover 的元素。这些信息不进入业务数据库，**却仍然是程序需要管理的状态**。
    - 教务系统讨厌的地方：**它把搜索做成了一个 database transaction**（输入 → 点搜索 → 返回结果）；但很多时候列表已经在视图里，我只需要一个过滤器。
    - 关系式：**`View = render(Model, ViewState)`**
    - Fowler 2004 的 Presentation Model，一句关键判断：**是否需要持久保存，与是否值得认真建模，是两件事。**
    - **MVVM**：Model（课程数据）/ View（筛选框 + 列表）/ ViewModel（筛选词 `query`、派生列表 `visibleCourses`）。
      - Vue：`ref` 保存 query，`computed` 描述"可见课程由课程列表和筛选词计算而来"（自动追踪依赖）；
      - `v-model` 封装两条连接：状态 → 控件（`:value`）与输入 → 状态（`@input`）。**所谓双向绑定，落实到这里就是明确的值传递和输入事件处理，并不意味着所有数据都可以随意双向流动。**
    - **React**：`DOM tree = f(state)`
      - 组件根据当前属性与状态描述界面；派生列表不必另存为 State；`setQuery` 请求下一次渲染，本轮拿到的状态仍是原来的快照；
      - 性能问题：一个网页有几万个元素，改一个字符全部重算 —— React 用 virtual DOM 把这些复杂性藏起来，**你只要按它的模型声明"状态是什么、状态怎么变"。**
    - **共同的思路（这才是要记住的）**：把变的东西和不变的东西分离开来；把逻辑和数据的源头分离开来。
      > **我们是 small head。在我们关注状态的时候，最好就不要同时关注状态是怎么变成 DOM 的。**

14. **把复杂性放进 Model 还远远不够。**
    - MVC/CRUD 对许多信息管理功能非常有效（业务对象稳定、一次请求完成一小段局部操作）——个人博客、课程查询、社交网络的基础功能都受益；
    - **但业务一旦跨越很长的时间，情况就变了。**
      - **长流程**：电商订单要经 下单 → 锁库存 → 优惠计算 → 支付 → 风控 → 发货 → 退款 → 售后 → 对账，任何一步失败都可能影响前后多个环节；
      - 用"当前状态"表示长流程（`order` 表加 `status` 列，或展开成一堆字段）会让状态机变得非常复杂，还要设计"触发风控后如何返回"；
      - 更糟的是："有的学生处于**既可以毕业、又不能毕业**的状态"——程序有 bug、或者有特批 override、或者错综复杂的逻辑最终使它处于"风控失败"却进入下一环节的状态；
      - **这种不一致的数据有时甚至是 silently corrupt（静默损坏）的。**
    > **根源：我们的业务流程既要编码过去、又要编码现在、又要编码未来。当前状态是一个快照，而它是从过去推演过来的——"它是怎么过来的"这个信息一旦丢了，不一致就会变得非常复杂。**

15. **复式记账：同一笔业务，保持会计等式。**
    - 规则：**每一笔交易都同时计入两个或以上的账户，且金额相等、方向相反**；可以试算平衡。
    - 会计等式：`资产 = 负债 + 所有者权益`。（"借""贷"是**记账方向**，不能理解为日常语言的借入借出。）
    - **但算得平不等于记得对。** 把业务归错类、重复录入一笔金额相同的借贷记录，都可能仍然平衡。原始凭证、业务含义和记账动作之间的对应关系，仍然需要核对。
    - 人类发明这种东西，正是因为**"一个当前状态很可能是 corrupted 的"**——所以要把"它为什么不对"在一定程度上找出来。

16. **记账架构：Event Sourcing + LLM as a Compiler（一个很漂亮的设计）。**
    ```
    Persistent History（发生了什么，不可篡改）
        ↓ LLM as a Compiler（把条目编译成一组记账动作）
    记账动作（报表_支出_财务费用(CNY(75)) 等）
        ↓ reduce：按规则执行状态变化
    当前状态（资产负债表 · 利润表 · 现金流量表）
        ↓ 人工审核 / 试算平衡校验
    ```
    - 讲者没有任何会计知识，于是**直接让 AI 设计一个"小的、像编译器一样的东西"**：从最终要交付的资产负债表所有可能的条目里提取出一组记账动作；每发生一笔业务，就用这组动作描述"货币资金会怎么样、所有者权益会怎么样、应付款会怎么样、现金流量表上会发生什么"。
    - 小技巧：GPT 一开始写的代码非常糟糕、非常长，讲者给它加了参数、把 state 确定下来，得到一个 **curry 之后的函数**（函数式编程里非常常用的技巧）——好处是**一笔业务在报表上的所有 side effect 都会被体现出来**，按时间顺序推一遍就得到当前报表。
    - **模型在这里像一个编译器前端**：把人的材料翻译成系统可以检查和执行的表示。语言模型负责提出符合材料的动作，**账本代码负责这些动作的确定含义和约束**；编译出来的动作是否符合真实业务，仍然需要审查。
    - 关键判断：**报表上的许多数字共同变化，但我们不希望让模型逐格填写这些数字，而希望它们来自同一组动作及其计算规则。**

17. **"当前状态"编码了过去、现在与未来。**
    - 过去：合同签订过；现在：正在等待打款；未来：货物交接、潜在的坏账。
    - **如果只盯着当前余额和一个状态字段，很多不同的历史就会被压进同一种表示中，很多尚未发生的预期又会与已经发生的事实混在一起。**

18. **Event Sourcing 把三样东西分开了：**
    | | 是什么 |
    |---|---|
    | **过去** | 事实——发生过什么，不可更改 |
    | **现在** | 视图——事实经过 dependency 计算得到的 |
    | **未来** | 预期——不是事实；如果世界没按预期发展，就**追加新的事实来矫正** |
    - 关键区分：**"发生了什么"（事件）与"希望接下来怎么样"（命令/预期）应当分开。**
    - **"过去不可更改"的含义，是不靠悄悄抹掉历史来解释今天的状态。**
      例：先前预计一笔应收款会收到，后来确认无法收回——这个结果不应使"曾经形成过应收"从历史中消失，而是按规则用新的事实改变当前的计算结果。**同样，"已经支付又发生退款"与"从未支付过"，虽然可能有相同的净现金变化，却不是同一段业务历史。**
    - 真实案例（成绩复核）：老师把卷面分"要回来"，发现最后一道题空着还给了 20 分，于是扣掉 → 这位同学挂了。**对数据库就是一次摧毁性的修改**：这门课学分要减一 → 影响"能不能毕业""能不能准出""能不能选下一门课"。**你已经选上了操作系统（先修是计算机系统基础），现在计算机系统基础挂了——你还能选操作系统吗？它内部天生就是不一致的。**
      → 用 event sourcing：**你手上握着所有的计算，把这个计算重新全部做一遍就行**；用自动的数据流分析，你都知道"这个从通过到不通过可能影响哪些结论"——因为 **data flow 被 make explicit 了**，而不是以状态的形式藏起来。
    - **推演未来**：卡在"支付"这一步，可以直接从这个位置推演——风控成功 → 状态 A；风控失败 → 状态 B。**只要有一个账本 + 一个模型，你就可以评估"我到底会不会破产、破产的概率有多少"。**
    - 为什么它更好：**它没有办法消除这些 essential complexity**（先修课程的依赖关系、毕业的依赖关系，这些事实已经存在），但是——
      > **event sourcing 把"事实、视图、预期"分开了。**
    - **跳出问题看问题，就一句话：现在是过去的结果。**

19. **教务系统：让毕业结论有一条可追溯的计算路径。**
    数据库里可能同时存着：成绩记录、已修课程列表、总学分、各类学分、"是否满足毕业条件"。**如果把这些都当作可以各自修改的独立事实，那么更正一门课的成绩时，就必须记得去修改后面的每一项。遗漏一处，系统里便同时存在几个互相矛盾的"现在"。**
    应该显式建模成一条数据依赖链：
    ```
    选课记录 / 成绩 / 认定记录
      →（加上去重 / 替代 / 分类规则）当前通过了哪些课程
      →（结合适用的培养方案）各类学分 → 课程准出条件是否满足
      →（毕业设计 / 资产归还 / 特殊政策与批准记录各自明确的判断）毕业结论
    ```
    **事实与规则作为输入，逐层产生结果。每个结论都可以追问："依据哪些数据，经过哪个计算得到？"**
    - 某门必修课从"不通过"更正为"通过"：系统记录这次更正、重新计算受影响的已通过课程、学分和审核结论，**并能解释为什么发生变化**；
    - 交换课程只能计一个类别、或两门合抵一门必修：**让认定记录和对应规则参与计算**，而不是在总学分字段上直接加一个数字；
    - 经过批准的特例也要有自己的位置（保存批准对象、适用范围和依据）。
    - 否则，**一个没有来由的"审核通过"，只是在隐藏复杂性**——下次重新审核时，系统仍然不知道为什么要通过。
    - 特别留意：**"课程条件满足"不能悄悄被当成"所有毕业条件都已满足"。**

20. **从状态一致性问题，转向计算正确性问题（全课的落点）。**
    - 对 SQL 的挑衅式批评：**它没有把跨数据的任意计算关系，充分作为一等公民来表达和维护。**（"一等公民"是指这类关系应当成为可以直接声明、组合、检查和追踪的对象，而不只是散落在应用代码里的一些约定。）
      具体问：**跨过数据库、应用逻辑、缓存乃至界面的计算依赖——一条基础记录变了，所有依赖它的结果由谁负责更新？怎样判断哪些结果已经失效？怎样追溯一个结果的来源？**
    - 现代框架都在"找补"同一件事：MVVM（提取展示状态）、React（界面从状态派生）、Dataflow（计算关系组织为流动与依赖）、Event Sourcing（当前状态从历史事实派生）。**它们都在尝试把"这个结果依赖什么"显式化。**
    > **设计原则：系统应保存足以重建其余信息的事实依据（source of truth），其他状态尽可能成为计算的结果。**
    - 为了性能可以保存汇总、索引和缓存，**但应当清楚它们从哪里来、何时失效、怎样重建**。一个业务决定如果必须由人作出，就把决定及其依据保存下来；**能够推导的东西，则尽量不要再引入一份独立的决定。**
    - **复杂性仍然存在，却从"怎样保证许多份状态永远一致"，转移到了"这段计算是否正确"。** 而后一个问题往往更容易管理：给定输入可以重跑、可以写有意义的测试、可以审计计算步骤、可以分析依赖。发现旧规则有错误时，也有机会在明确的适用范围和时间边界内重新计算，而不是对着一堆已经失去来源的数字逐个打补丁。
    - **两个必须先想清楚的前提：**
      1. 要复现当时的结果，就必须知道当时使用的规则和外部输入（哪一版培养方案、某次计算采用的汇率），**不能偷偷换成今天的数据**；
      2. **重放账本可以重新计算余额，却不能把已经完成的付款再执行一次**——对外部世界的动作，需要与内部状态重建区分开来。
    - **对生成式软件工程的意义：**
      > 让 AI 面对散落各处的隐含同步要求，它就需要反复猜测"哪些地方必须一起改"；而**把事实、规则和依赖表达清楚之后，生成与检查才有了共同的对象**。
      > 代码越容易生产，我们越有理由认真选择这种表示——让系统中的每一个重要结果，都能回答：**"我是怎样算出来的？"**

### 立刻能用的做法

- 设计数据模型时，把"能推导的"和"必须作为决定的"分开；**能推导的就不要存成独立字段**。
- 你的项目里凡是出现"某个结论字段"（是否合格、是否完成、总分），先画出它的依赖链，让它可重放、可解释。
- 与 AI 协作做不熟悉的领域（会计、教务、生物）时，**你自己不做领域建模，而是让 AI 造一个"编译器式"的中间表示**，然后你审查编译产物是否符合真实业务。
- 想要"可生长的架构"，就问自己：**如果明天加一类新需求，我今天是固定协作规则、保留局部选择了吗？**

# 第八单元 · Agent Native 开发：从 Ralph Loop 到"把工程知识放进环境"

**核心一句话：一次回答解决不了问题，就让 Agent 反复尝试；Agent 会漂移，就让每一次状态迁移都停下来检查；检查要真的关得住，就把它写成 Spec、挂到事件上、放进 CI。**

### 重要观点

1. **AI 给我们的最大能力：你随时随地都可以开始。**
   - 哪怕最开始只有一个想法，也可以直接让它往下走；到不了那么深、维护不下去了，再回头调整；
   - 在讨论过程中随时让 AI 生成一版，然后比较：**变好了还是变坏了？趋势上是变好还是变坏？** 变坏了就再讨论一轮、再做一版；
   - AI 实际上承担了一个员工甚至一个团队的职责。讲者自己的做法：**一个 tmux 窗口分成四份，四个 Agent 并行**——"最多只能开四个，不然我的大脑跟不上 AI 输出的速度"，而他自己做的是**监工**。

2. **let it fail（不是鼓励随便交差，而是允许原型暴露我们的错误）。**
   - 实现可能没有满足规格，规格也可能没有真正表达需求；
   - 即使两者都对上了，**需求里关于用户、规模和运行环境的假设仍然可能不成立**——纸面上说得通的选课系统，遇到两个人同时抢最后一个名额，就可能露出另一副面孔。
   > **当成本足够低的时候，就应该让 AI 先承担一部分"预测"**：这个架构换个人用会怎么样？用户多了会怎么样？两个模块之间有没有我未曾想过的交互？
   > **"我现在没想清楚，不要紧，你给我搓一个；搓完了以后拿我的 use case 去评审一下。"** 构建原型的能力，是 AI 给我们的一件非常好的礼物。

3. **软件工程解决的是一类搜索问题。**
   intent 到 spec 是一对多的，spec 到 implementation 又是一对多的。如果有一个 review 能跟你来回讨论、经过几轮迭代达成共识——**最终的方案可能远好于"一条线走到黑"**。一条线走到黑的方案，其可维护性、可观测性可能差十万八千里。

4. **模型为什么不会一直尝试下去（机制解释）。**
   强化学习的重要奖励信号是"你要完成任务"。**如果花了很多时间还没完成，你就拿不到奖励。** 所以它倾向于一个比较短的 BFS，一旦找到一条自认为合适的路线就继续往下。
   （有意思的现象：DeepSeek 的思维链想想想一段时间，**如果任务太难，它就会摆烂**——"这个任务我解决不了"，然后直接停下。这是受了强化学习影响的。）

5. **150 行的 ReAct Agent：bash tool 就是全部接口。**
   工具面就是一个 bash（`type: function`，`name: bash`，一个 `command` 参数）。主循环就是一个 while：
   ```
   读取用户输入 → 构建 messages → 调用模型 API
     ├─ reply 里没有 tool call → 输出 reply，本轮结束
     └─ 有 tool call → 取参数、执行工具、把 tool result 与 tool_call_id 追加进 messages，回到调用 API
   ```
   **为什么建议每个人都自己做一个**：你有一个想法就自己做出来，再和成熟的东西比一比，看那个增量——**你先了解一个简单的核心，再去知道复杂的东西多做了什么**，就能体会一个软件从小到大膨胀的过程。
   （安全提醒：**保护好你的 API key**——不锁屏时室友可以 `cat` 一下、拍张照。）
   **一个 toy project 与真实 project 的差别**：他在小 agent 里 hardcode 了一个 timeout，而真实环境里 agent 常因对环境的感知不够好而设出不合适的 timeout（比如墙内访问 GitHub：你认为的速度和实际速度不一样——"我的世界观一直在这个地方，所以我 overfit 了这个环境"）。**这就是最小原型与产品之间的 gap，它可能需要一个架构来补。**

6. **Ralph Loop：三行脚本。**
   ```bash
   while true; do
       cat PROMPT.md | claude -p
   done
   ```
   名字来自《辛普森一家》的 Ralph Wiggum——**有点笨、有点可爱，但从来不放弃。**
   实质：**同一个任务、检查、修改，直到无法改进。**
   > **The prompt stays the same, but the world changes.**
   每轮提示词都没变，**变的是工作区**：上一轮实现了功能、留下了测试结果、记录了失败原因，下一轮接着这些状态继续。
   **但必须记住：`while true` 本身不会判断"无法改进"；何时停止需要另行约定**（验收条件、预算或停止条件）。

7. **会漂移的模型：舔狗、屎山与"扶起来"。**
   导师可以对学生说"你这代码是零分的，再拿这种代码来就不要来见我"——学生会痛，但会理解，下一个版本会把架构全部推掉。
   **模型不是这样的**：如果上下文里加载了你的 slop 代码，它就有一个强烈倾向——**"我的任务是把这段 code 扶起来"**。当它说"这个架构要重构"时，重构很可能不能保持行为百分之百一致；**而你的代码正在线上跑着，你只想让它花一分钟把项目扶起来、别让服务崩掉。**
   > **它遵循指令有道理，不遵循指令也有道理。而在这种两难里，它选择遵循你的屎山代码，把项目一点一点往泥潭里拖。**
   解法是**搜索**：让模型停留在 design space 里做 BFS，再适当做 DFS，用 prompt 或 loop 管理这个搜索空间——**Ralph Loop 就是一种线性的管理方法。**

8. **Everything is a state machine（理解 Ralph Loop 的关键视角）。**
   - **状态 = 工作区**：不只包含当前代码，也包含需求、设计文档、测试用例、运行结果、日志和待办事项。刚开始可能只有一个 `spec.md`；
   - **迁移 = 一轮工作**：同一个任务做一轮，把状态变成下一份状态——**顺手做一个 git commit**。
   于是**一次开发就是一次状态迁移**：从"这个功能尚未实现"→"已有实现但测试失败"→"失败原因已定位，修复通过了检查"。
   可以要求：每次不要做太多、做完以后要检查、还要 review（可以让另一个 Agent 来做）。
   **它是一个 non-deterministic 的状态机**：同一份状态上可以执行不同的操作（用 GPT 做一轮 + commit / 让 DeepSeek 做一轮 / 让 Claude review / 修好并通过检查 / git merge）——**这又回到了那个 search procedure**。
   还有时间维度上的动作：**每隔一段时间做一件事**，比如每星期做一次架构级的 code review，看项目有没有变成 AI slop。如果已经变成 slop，就进入一个**"重构 agent"**（可以设计得狠一点：把所有 AI slop 和相关的东西直接删掉、做一个 commit，再让一个 agent 用更好的架构重新实现）。
   → 加上 **subagent 并行**（"重构 A 模块"和"重构 B 模块"可以同时发生，最后 git merge），就有了这个正反馈：
   > 早期的 ReAct Agent 跑着跑着就漂移，上下文一爆就越做越差 → 我们用外层的循环让它完成更强的任务 → 模型厂商把"一次 session 里能完成的任务"再调高 → 我们再套一层 loop——**就这样左脚踩右脚，开始上天。**

9. **对照实验（Ralph Loop vs 直出）。**
   同一个任务"给我做一张属于我的名片卡片"：
   - **直出版本非常 fancy**（玻璃动效、小巧的 Mac OS 终端），但**把主页邮箱写错了，还把讲者标注成一个他并不属于的机构**；
   - **Loop 版本朴素多了**："计算机学院副教授"，邮箱是对的，还找到了他的 GitHub，也是对的。
   （肯定有随机性，不能断言谁绝对更好；但可以看到：**同一个模型，你投入算力、投入 prompt，最后得到的结果差别会非常非常大。**）
   给所有人的建议：
   > 网上有各种各样的 prompt 和 skill，你可以复用；但最终你可能会发现，**最后还是自己写的那个 prompt 最懂你**——因为你和模型有长期的磨合，磨合以后你才能比较好地理解：**什么时候应该放它去做，什么时候应该不信任它。**

10. **这个 design space，地球人都不知道（务实的态度）。**
    - Codex 还是 Claude Code 还是 Pi 更好？不知道；
    - Pi 生态里 subagent 插件不止一个，哪个更好？不知道；
    - **很有可能你上一个版本里 work 得很好的 prompt，下一个版本模型来了就全变了。**
    > **工程建议：新模型发布的时候，把那些系统提示词和 skill 全部拿掉，然后拿一个你比较熟悉的任务做一个背靠背的对比。** 你可能会发现，拿掉那些 prompt、skill 之后模型反而表现得更好。

11. **那条最重要的提示词：**
    > **每轮先检查当前状态，只推进一个明确的步骤，然后验证并评估结果。**
    前提假设是"Agent 训练得不够好，或者在你当前的上下文下可能发生漂移"。所以让它先做一个比较小的状态迁移，然后**在这个状态迁移处把它停下来：wait，然后做检查**。检查可以是让另一个 Agent（另一个模型）来 review 这次提交，也可以是跑测试、检查脚本。
    **这可以在一定程度上阻止状态漂移，而且这些检查对整个项目的推进也是有进展的。**

12. **开发者是不可信的（两条公理 + 人的投机）。**
    - 公理一：**机器永远是对的**——不要怀疑机器；
    - 公理二：**你写的代码永远是错的**——所有东西出了问题，你不要埋怨别人。
    - "我今天就改这一句话，应该没事的吧"；"循环变量从 1 改成从 0 开始，应该没事吧"；"我这单元测试通过了，应该没问题吧"——**人是有自信的，而人的自信就带来了开发者的某种不可信。**
    - 另一层不可信：**投机**。"反正交一次又不花钱，也许十秒钟就得到一个对的反馈，fast pass 就过了；如果不对，再回到 slow pass。"

13. **祝贺你，重新发明了 CI/CD。**
    既然开发会不断改变工作区，而我们希望每一个进入主干的状态都是"好"的——**在每一个状态后面都做一次检查**：通过就继续；不通过就拒绝这次 loop 的结束，回到上面把所有问题修好。
    > **你不应该相信任何开发者。** 你进公司第一天就跟实习生说"做好测试、做好测试"，他不会去做——就像老师不断说做算法题要写测试，你们不会的，**因为你们是投机的**。
    > 所以如果你不相信实习生，**你就把所有的门控全部写在脚本上；而且非但要写在脚本里，你还要不让他去运行它——因为你也不相信他会运行。**
    三个名字的分工：
    | | 含义 |
    |---|---|
    | **CI**（Continuous Integration） | 频繁把小规模改动集成到共同主干，**每次集成都自动构建、验证** |
    | **CD**（Continuous Delivery） | 软件始终处于可发布状态，**什么时候真正上线可以由人决定** |
    | **CD**（Continuous Deployment） | 通过检查的变更**自动发布给用户** |
    （历史：1990s Kent Beck/XP 推动频繁集成 → 2000 Fowler 总结持续集成、2001 CruiseControl → 2010《Continuous Delivery》把 deployment pipeline 系统化。）
    **Pre-LLM 时代学生不理解 CI/CD 的原因**：它通常被集成到生产流程里（容器创建、独立于你机器的环境、同步到企业流程、页面上看结果）。

14. **Hook：事件发生，执行指定动作。**
    > **你需要把动作落实到明确的事件上，而不能只是期待它记得做。**
    开发流程里有各种各样的事件：commit、push、发起 PR、merge 到某个分支/protected branch。你可以把 hook 加在一个 transition 之前或之后。
    **两个关键区分：**
    - 本地 `pre-commit` 便于及时反馈，**但可以被 `--no-verify` 跳过**（Git Hooks）；
    - 远程检查**配合 required checks 与分支保护**，才能让失败真正阻止合并。
    > **也就是说：有检查，和检查有约束力，是两回事。** 如果测试失败后仍然能照常合并，检查只是在一旁亮了一盏红灯。
    **lint**：泛指不运行程序、只做静态分析就能发现的代码检查。
    > **lint 基本上就是软件工程里最基础一级的守门员：如果你这个都过不了，就不要谈软件工程了。**
    （还有"薅算力羊毛"的便利：GitHub Actions 每月大概 2000 分钟；甚至可以**在 GitHub Actions 里"养"一个 Claude Code**：push 一个"我要做什么"→ 拉起 Claude Code 修改 → 再提交 → 再次触发 hook。**前提还是那句话：你要有一个软件工程的概念——什么时候应该跑什么。**）

15. **把 CI/CD 写成 Spec（可验收的做法）。**
    任何业务系统都会很琐碎，今天你可以把配置交给 Agent，但**你仍然要表达清楚希望系统怎样工作**：
    - **合并的条件**：CI 必须要求 Lint 通过、测试通过；PR 有新提交就重新检查；合并前验证它与最新主干的组合；检查失败就禁止合并，并把要求落实为**分支保护规则**；
    - **发布的条件**：通过 CI 后，根据 main 生成页面并部署；main 更新后重新运行 Lint、测试和页面构建；全部成功才部署这次构建的产物，失败则保留上一版。
    - **验收这套流程时，也应该观察失败路径**：故意引入一次 Lint 错误，确认它真的阻止合并；让测试失败，确认没有发布新页面；再修好错误，确认能正常更新。
      > **这样检验的是"门是否真的关得住"，而不只是"配置文件看起来像那么回事"。**
    - **Lint 与测试承担不同职责，不能因为其中一项通过就省掉另一项。**

16. **CI 在 Agentic AI 时代的含金量（本讲最实用的一节）。**
    > **CI 的 first principle 是"开发者不可信"。而 Agent 就是那种最不可信的开发者——因为 Agent 和人类天生是不对齐的。**
    **你会经常看到它做这种非人类做的事情，人类是不可能做的：**
    - **一写就是 20 KB 的文档**——你说写个文档吧，它 check in 一个 20 KB 的文档，你看两行就进入无穷琐碎的细节；
    - **事无巨细地交代细节**——那段代码其实已经 self-explain、连注释都可以不要，它硬生生把思考流程、在 agent loop 中遇到的问题一个一个写进文档；
    - **于是出现了那个很致命的结构**：`doc.md` 和 `implementation.py` 之间是有关联的，但今天基于 repo 的维护方式里**这个关联你看不见**——它只在"你写的那一刻"存在；下一次换了 agent、或者上下文被压缩了，它根本不记得这两个文档要保持一致；
    - **一旦文档和代码不一致，到底听谁的？不知道。** 整个项目就开始滑向 slop 崩溃的边缘；
    - **过度反应**——在不重要的细枝末节上疯狂出力，而对 design space 里最重要的部分视而不见；
    - **用工具填满你的上下文**——做网页就截图、用 Chrome DevTools，疯狂使用工具填满上下文（好例子：GitHub trending 上用 subagent 做浏览器 verifier，只把最简短的 summary 放回主上下文，而不是把截图塞进去）；
    - **写出人类无法阅读的代码，并且自己非常自信可以维护。**
    > **如果这个项目今天还需要人共同维护，你就必须强行阻止 AI 做这些事。**
    > 因为一旦中间某一件事情发生了，就永远无法回头：一旦成为 AI slop，人就再也无法维护它——那个文档你能改吗？你想在文档里定位到你想改的地方都不可能；你唯一的可能，就是**让 Agent 继续改，直到这个项目维护不下去**。
    > **CI 阻止，Agent 修正。**（类比丰田的 **jidoka**：发现异常就停线，把质量检查放进生产过程。）
    具体怎么做？在 CI 里创建一个**硬条件**——比如**文档不能超过 1000 字**。这是代码就能判定的：把字符串量一下，超过就直接 fail。
    有意思的是 Agent 的反应：**它可以看到这些检查**，它可以在本地运行 pre-commit hook，马上发现失败，然后想起来 `README.md`/`AGENTS.md` 里写着"文档禁止膨胀"。
    但注意边界：**今天的 Agent 还做不到"记住"**——即使有 100 万上下文，随着整个上下文膨胀，**Agent 的注意力会不断涣散、不断滑坡**，当项目到达 10 万行或更多级别时。
    → **"文档不超过 1000 字"这类检查在 AI 时代变得非常重要**：这样的规则一般情况下不会有人做（文档是人写的，人积累 slop 的速度远没有 AI 快，重构相对容易）。

17. **把 Agent 的偏执变成可执行的约束（关键的两列表）。**
    | 常见问题 | 自动检查 | 人工判断 |
    |---|---|---|
    | 一写就是 20 KB 文档 | 文档字数预算 · 重复段落检查 | 内容是否值得保留 |
    | 堆细节、造多余抽象 | 重复率 · 未使用代码检查 | 抽象是否必要 |
    | 小任务变成大重构 | **改动范围白名单 · Diff 预算** | 超出范围是否批准 |
    | 代码能跑但读不懂 | Lint · 类型检查 · 复杂度上限 | 命名与设计审查 |
    | **改测试，让失败消失** | **受保护的回归测试 · 测试删除告警** | 行为变更是否合理 |
    | 顺手关闭 CI 规则 | **规则文件变更须指定人批准** | 批准者与开发者分离 |
    > **底线：负责修改代码的 Agent，不能因为过不了检查，就单方面把标准调低。**
    > **删掉失败断言得到的绿色，与修复程序得到的绿色，颜色相同，含义完全不同。**

18. **Agent Native = Ralph Loop + 门控。** 把前面串起来：
    - **Ralph Loop**：以 workspace 的状态为状态，用 Git，选择某一个 action 向后做一步；
    - 在做的过程中，做 pre-commit、post-commit、pre-push、pre-merge 这些各种各样的门控检查。
    **这就是 Agent-native 开发。**

19. **Harness engineering：从空仓库开始（OpenAI）。**
    > "We started with an empty git repository."
    **人从零开始不写代码了，但人依然要把这个流程定好：环境、约束、反馈和验证机制。** 而这些可能是用自然语言说的（"我每次在 push 之前都要确保代码的明文没有泄露、API key 没有泄露"）。
    围绕 Agent 建立的运行环境、工具、约束与反馈机制，常被统称为 **Harness**——**它是让模型的能力能够稳定用于具体工作的整套配套设施。**
    > 所以 **Agent-native 开发不仅是"代码由 AI 写"，还包括让工程知识成为 Agent 找得到、用得上、能够验证的东西。**
    两个具体问题：
    - **让 Agent 找得到**：人类脑中的工程知识必须**外部化**，并组织成 Agent 能发现的、版本化的状态；**AGENTS.md 做目录**，设计、计划和决策放进仓库，按需查阅（不必把所有知识一次塞进去）。
      > **"我们一直这样做"对刚开始一轮工作的 Agent 没有意义。**
    - **让 Agent 看得见**：让 Agent 能**直接观察程序行为**，而不是依赖人类描述结果；每份工作区能独立启动应用，Agent 自己操作页面、查日志、复现 bug。如果每次都等人转述"按钮好像没反应"，反馈既慢又容易丢信息。

20. **把品味做成机制。**
    - **让约束可检查**：把重要的架构品味（"页面组件不能绕过业务层直接访问数据"、"这类日志必须带必要字段"、"错误处理要沿约定接口传播"）转化为**可检查的规则**，而不只是写在规范文档里。依赖方向用 linter 检查，**报错信息直接包含修复指导——只返回一个红叉，会让 Agent 花时间猜规则**；
    - **让修复持续发生**：技术债不是等到代码无法维护才清理，而是持续进行小规模修复；**后台 Agent 定期扫描偏离规则的代码，提交小规模重构 PR**。如果生成代码不断复制已有的不良模式，等到全仓库都长成同一种坏样子再修，成本就高了。
    （边界提醒：**哪些规则值得固定下来，本身仍然需要判断——不能把"文件短"简单等同于"设计好"。**）

21. **门控的三个参考实践。**
    - **Codex 的三层门控**：pull request 时跑快速门禁（lint、格式、拼写、bad smell 如文件/函数过大、大文件策略、依赖）→ main 上跑全量认证（大量单元测试）→ 发布时再打标签。
      （讲者的"ClosedAI"吐槽：文章最重要的一句是 **"What we're still learning"**——如果一个软件要以年为周期维护，他们的 Agent flow 还没想好；文中**没有**附上那个内部项目可直接复用的完整门控配置。）
    - **Stripe Minions**：用 Blueprint 组织混合工作流——**实现任务、修复 CI 失败由 Agent 决定怎么做；运行 linter、推送分支直接执行普通代码、不调用模型。** 预算规则很克制：**完整 CI 最多跑两轮**（本地修 lint → 推送跑 CI → 无法自动修复的交给 Agent 再修一次 → 第二次推送后，分支交回人类审查——**团队认为继续重试的收益会递减**）。
      > 设计思路：**如果某一步每次都必须执行、且执行方式已经明确，就把它写进流程。** 模型适合处理需要理解和选择的问题，固定工序可以由程序可靠地完成。**重试也有成本：连续失败时，应该判断反馈是否带来了新信息，而不是把"再试一次"当作永远正确的回答。**
    - **Anthropic 的 16 个 Agent**：并行 Agent 会卡在同一个 Bug 上——开始编译 Linux 内核时大家先撞上同一个 bug，重复修复、覆盖彼此的改动。
      **解法（很值得学）**：**用 GCC 构造可以独立验证的子任务**——大部分文件用 GCC 编译，只把不同的子集交给新编译器；失败后把部分文件换回 GCC，逐步缩小导致失败的集合；于是不同 Agent 能去修不同文件暴露的问题。
      > **验证方式改变了任务的可分性**：原来只知道"整个内核编译失败"，大家只能涌向同一个入口；有了可信的参照和可缩小的失败集合，就能把大问题拆成可以分别推进的工作。（仍需检查文件组合：有些文件分别过关，放在一起却失败。）
      **两条结论**：①**增加 Agent 数量之前，先改善任务表示和反馈，可能更有效**；②Ralph Loop 真正落地时，还需要一个 **orchestration 的调度 Agent** 来协同大家的进展，甚至让大家"看到"进展。

22. **把进展画在架构图上（讲者自己的做法）。**
    - 一份 `architecture.md`，可以自动生成一张架构图；
    - Agent workflow 里有一个 **log book**，里面有很多 task：有些已完成，有些 ongoing；
    - 有一个 **Agent dashboard**：每个 ongoing 任务自动推到 GitLab CI，于是在架构图上就能看到**有几个 Agent 在完成这个任务、一个估计的百分比进度条、在哪个模块上干什么**。
    → 对管理者的价值很直接：他作为总架构师只要看这张图就够了——**知道底下在干什么，可以预估一小时以后项目会变成什么样，然后决定要做什么调整。**
    （下一步还没敢做：让一个 **master agent** 来派活——所有事都交给它，它帮你在 log book 里开好多个任务、挂上去。）

23. **DeepSeek Harness：一个把经验写成门禁的项目（本讲的标杆）。**
    **背景故事（很朴素但很真实）**：这是中国人的项目，作者选择用中文写文档——因为**读中文比读英文快一倍**，而就是这一倍让他能快速浏览文档、定位到想找的地方。但作为要走向世界的项目，就得同时维护中英文两份文档——**"这不就是地狱和灾难吗？"**
    **机制：「三套件 + 一个门禁」。** 每一篇文档在被覆盖的范围内，都是同一目录下的三个兄弟文件（`docs/i18n/README.md` 定义配对契约）：
    ```
    foo.md          # 正文（中文或英文，看谁先写）
    foo.zh.md       # 另一侧的翻译
    foo.i18n.yaml   # 配对记录：两侧内容的哈希
    ```
    几条很讲究的规则：
    - **没有 locale 目录、没有独立翻译仓库、没有中英交错的文件**——三套件就在同一个目录里，牺牲的是目录的干净；
    - **两侧权威对等**：谁先写，谁就是"这一次的原"，另一侧翻译过来；绑定它们的是"**必须说同一件事**"；
    - **一致性由程序机械校验**（`pnpm run verify-translation-pairing`，属于 doc-sync，CI 全量跑）：
      - 三套件齐全，**缺一即红**；
      - `foo.i18n.yaml` 按英文标题 slug 路径逐条记录中英文的 sha256 前 16 位哈希；**哈希跳过代码块和生成区块**（这两类本来就要逐字节相同）；
      - **谁新谁旧由 git 历史明确判定**（没见过的新 hash 就是新的），然后用 AI 帮忙翻译——**而且是 patch-based 的：看这份文档改了什么，把另一份对应位置的部分也改掉，其他地方保持一致。最小补丁，不重新翻译。**
    - **聪明的收尾**：牺牲了目录的干净，就用 IDE 的投影把它藏起来（VS Code 忽略 `*.i18n.yaml`，中文使用者把英文文档全部隐藏）——"我看到的就是所有中文文档，用起来一模一样"。**你可以得到一模一样的开发体验，但它同时是一个 Agent-native 的东西。**
    **几个值得单独拿出来的点：**
    - **style samples**：风格样例目录（里面"还是有一些 AI 味的"），作用是**把"人感"当成可校准的规范**；
    - **按需加载（渐进式披露）**：这些规范**不是塞进 `AGENTS.md`**，而是放在只在需要写文档、需要翻译文档时才被加载的地方。理由很实际：**如果把所有 specification 都放进 `AGENTS.md`，随着项目暴涨，甚至 100 万的上下文都装不下**；
    - **terminology（术语表）**：约定中英文术语的统一译法，**也可以被门控检查**——既然中英文在 paragraph/section 级别一一对应，就可以要求某个词的出现频率有一致对应（英文里 `AI` 的次数与中文里"人工智能"的次数，差值应落在某个范围内）。**要小心调这个决策边界：不要把实际上可以通过的给筛掉。**
    - **为什么值得做**：因为这种漂移太常见了——**当你不约束 Agent 的时候，它会以光速生产 slop。**
    **从 git 历史看经验是怎么长出来的**（这个项目从空仓库起步，把开发历史都留在 git 里）：
    - 2026-06-10（深夜）第一个提交，空仓库起步；
    - **2026-06-25：术语先行**——没有任何机制，只有词汇的约定（说明他们**意识到文档这件事的重要性**，是有经验的人）；
    - 7 月 3 日：引入**对等权威**，随后引入**配对契约**；
    - **而且在很短的时间内，他们就发现这个机制必须强行进入自动化的流水线，而不是停留在人的约定上。**
    **设计的来源猜测**：Pre-LLM 时代也有类似方式——Python 的 **docstring 生成 pydoc**、Java 的 **JavaDoc**、C++ 的 **Doxygen**：照语法写注释就能被提取出来，代码和 API reference 保持百分之百一致。**受到这些启发，在 Agent-native 时代要把人的工作迁移给 Agent 时，配对契约 + 门禁就是一个非常酷的机制。**
    **还有哪些门禁（多到"非常稳"）**：`AGENTS.md` 分层（每个目录下都有，构成常驻的指令体系）；**`verify-doc-budgets`**（给文档设量化预算，root 与 architecture 两类分别有上限——**防止 AI slop 无限堆积**）；agent notes（Ralph Loop 的条目分 **implemented / proposed / rejected / archive** 四种状态）；各种 verify（client、UI、verifier、translation pairing、application entry points、TypeScript 相关）；**`verify-type-equivalent`**（文档里粘贴的类型必须与源码一致，且不允许漂移）；本地自证 + CI 门禁 + 人工评审；新增文案必须通过语义评审；**链接一致性**（所有链接都要合法）；**代码块一致性**（如果文章里的代码块是个 interface，它会检查这个 interface **原封不动、每一个字符都逐字出现在某个文件里**——这样杜绝了"代码改了接口、文档没跟上"或"文档改了接口设计、代码没跟上"）。
    （讲者他们又做了一点扩展：**代码块带执行语义**——在 Markdown fenced code block 语法上做轻量扩展，"specify"这段东西是干什么用的、需要它出现在某个位置、或与别的东西以某种形式关联，然后有轻量级的 check 去检查它。）
    **代价与"监工"的位置**：这么多机械门禁，代价是每次提交前可能都要运行大量门禁。但**重要的平衡是**：
    > **你又不写代码，大部分时候你都是监工。你写 plan，你和 AI 一起写 plan**——在 plan mode 里先把"要做什么、做到什么程度"搞清楚，然后剩下的事情不是我们做的，是 AI 做的。
    > **而且我改 log book 的时候，不需要运行那些 CI——因为代码没有动过。**

24. **真正的经验（本章的着眼点）。**
    - 真实的负载、依赖和异常，会暴露原型里隐藏的设计假设；
    - **你很难凭空想到所有这些有效的边界和反馈方式；只有真的做过、失败过、修正过，才会知道"这里必须有一道门"。**
    > **模型之外，还有一整套让工作得以推进的装备。**

25. **垃圾回收解决不了的问题。**
    我们可以把日常清理类比为垃圾回收（消除重复、修正文档、统一接口、防止坏模式扩散）。**即使这些工作全部做好，系统仍然可能建立在一个已经失效的设计假设上。**
    例子（数据库架构）：假设所有用户数据都可以集中在一个写入节点、其他节点保留完整副本分担读请求——用户少时非常直观；但**写入和数据量持续增长后，增加读副本未必能解除瓶颈，因为每个副本仍要承担全部更新**。**把代码整理得再漂亮，也不会自动改变这种负载结构。**
    → **失败在这里提供的价值，是帮助我们看清应当改变哪一层设计。**

26. **Friendster：看出怎么改，还要改得动。**
    社交网络先驱 Friendster 迅速吸引大量用户，随后延迟、宕机频发，在竞争中掉队。亲历工程师 2006 年的复盘讨论了实际问题：**单主库带多个完整副本，每个副本都要重放写入，I/O 压力导致复制延迟**。他提出**按用户拆分数据**，让不同服务器只承担部分数据与负载；但据其叙述，**这个方案没有在 Friendster 顺利推进，容量问题的根因并没有被解决**。这套设计后来在 Flickr 落地。
    > **看出架构应该怎样改，和组织真的能够把它改掉，是两件事。**
    及时重构既要求技术判断，也要求团队有能力调整分工、迁移数据、安排上线，并承担变化过程中的成本。**一直修补局部症状，可能只是在更认真地维护一个已经不合适的前提。**
    （讲者补了一句：这是 Pre-LLM 时代的事；在今天，**也许 Agent 真的能把它扶起来**。）

27. **一个社会性的威胁（本讲最后、也最重的一段）。**
    - **好想法也会 slop 化**：你的 intent 方面确实可以是一个世界级的想法；但如果你组一个草台班子去做，进入的很可能就是一条直线——**海量产生的 AI slop，最后这个好想法被别人抄走**。而一个有经验的团队，才可能收敛到一个更好的方向。
      历史案例：**Webvan**（网上买菜设想不难理解，但仓储配送设施能容纳多少订单与**实际能获得多少订单**是两个问题；2000 年年报披露配送中心业务量低于原设计容量的 40%，订单量也低于盈利所需水平——**如果需求密度没有得到验证，庞大的仓配系统会把一次判断错误变得昂贵**）；**Quibi**（有内容、有技术、有产品形态，**并不等于用户需要这样一个独立服务**）。
      > **Agent 让实现更便宜，却不会使这些问题消失**：一个好想法可以迅速生成许多页面、文档和功能，也可能逐步 slop 化——**看起来越来越像成品，重复、冗余和未经验证的假设却越来越多。局部测试不断通过，真实用户仍然可能不愿意用；代码越写越多，原先需要检验的关键假设反而被埋住了。**
    - **没有 token，就没有做很多次尝试的机会。**
      > **尝试的机会：没有 Token，就没有做很多次尝试的机会 → 实践机会的差距，会积累成判断力的差距。**
      > **学习好的设计：同时需要很强的学习动机 + 学习能力。**
    - **斩杀线：从博士生到本科生。**
      如果你读完博士的时候依然不如 Agent 好用，用人单位会**选一个 senior、给他无穷的 Token，而不是去培养一个 PhD 学生**。因为资本要做的是最大化企业的运行效率——**如果回报周期实在太长（需要四五年才能达到 Agent 的水平），那时候公司早就黄了**。
      > **而问题是 Agent 现在就在这条线上，而且 Agent 自己还在上涨。**
      这条线现在已经越到了本科毕业：**"本科生毕业的时候，你还有没有一个 20 美元的 Claude Pro 的价值？"**（"能达到 Opus 4.5 水平的本科生，我觉得非常困难。"）
    - **大学、资本与新的教育形态。** 讲者认为这个问题的解决**可能只有在大学里能解决**（大学是非盈利的）。但现实是：考核老师的指标不是上课而是科研经费，高校也越来越资本化——只不过这个资本体系由基金委、科技部组织的优青/杰青/院士构成金字塔，**在这个金字塔下面，每一个层级的产出都类似于公司的产品**。
      > **当学生永远赶不上 Agent 的时候——老师和学生都被斩的时候——这个体系就完全失效了。**
      反过来他认为**某些教培机构可能是一种新形态的大学**：靠样板课、从上到下资本化运营；花 100 万雇一个清北天才设计样板课，上完之后每个老师都是执行的机器；**现在把"老师是执行的机器"换成"老师 + AI"，同时花 1000 万抢最好的天才来设计样板课——它就完全颠覆了教学教育体系。** 而大学没办法："我们的惯性很大。"
      > **非常感谢开源社区。尤其是我自己，我这一切都是开源社区给的。如果我不在开源社区里看到那些好的东西，我就不会有今天的理解，也不会有今天来上这门课。**

### 立刻能用的做法

- **给自己做一个 Ralph Loop**：一个 prompt 驱动；每轮先检查当前状态，只推进明确的步骤；未完成时**把下一步写进文件**（所有状态都在 repo 里）；只有整个任务确认完成才输出 `done` 结束循环。
- **每一个状态迁移后都停下检查**：测试、lint、结构检查，或者让另一个模型的 agent 来 review 这次提交。
- 把门控**写进 CI 并加上分支保护**，然后**故意制造一次失败**，确认门真的关得住。
- 对 Agent 的高频病症写**代码可判定的硬条件**：文档字数预算、diff 预算、改动范围白名单、受保护回归测试、规则文件变更须人工批准。
- **让工程知识外部化**：`AGENTS.md` 做目录 + 设计/决策/计划进仓库 + 每份工作区能独立启动应用让 Agent 自己看行为。
- **改 log book / plan 时不用跑 CI**——因为代码没动。**你的位置是监工。**
- 每隔一段时间做一次架构级 review；**该重构就重构**（必要时开一份新的白纸，一点一点把旧功能迁进来，保持好架构）。

# 全课总结 · 十句话

1. **软件工程 = 补上 Intent → Spec → Impl 之间的 gap；AI 让 implementation 变便宜，杠杆转移到需求与架构。**
2. **一切补救的本质，都是把发现问题的时间点提前**（Royce 1970）——所以要做 MVP、要 TDD、要小步走。
3. **给模型模糊的意图，它很容易"自认为完成了"；给模型完整的规格，结果才变得确定且可验证。**
4. **Verifier 是第一原则**：任务可验证，Agent 就能不计代价地尝试；开放问题要**分解成许多可验证的小子问题**（用算力换智力）。
5. **Agent 是"急着完成、过度遵循、不会猜你没说的约束"的开发伙伴**——所以你必须写清约束、每一步检查、并且在关键处自己做判断。
6. **CI 的 first principle 是"开发者不可信"，而 Agent 是最不可信的开发者**——把品味写成可执行的约束，用事件挂住它，并且让检查真的有约束力。
7. **好的架构不是选出一个解，而是设计一片会生长的解空间**：固定协作规则，保留局部选择。
8. **保存 source of truth，让"现在"从"过去"计算而来**：把状态一致性问题，转化为计算正确性问题。
9. **每件东西都可以追问"为什么它这样设计"**（Virtual Implementation）；经典与开源是你最重要的老师，**教科书是有损压缩，一手资料更好**。
10. **在这个时代真正稀缺的不是"会写代码"，而是——能找到值得解决的问题，用证据让坏方向及时停下，并对长期结果负责。**
